# M3.5 — Performance-history data model

GitHub issue: [#30](https://github.com/andywrussell/caddai/issues/30)

## Goal

Add a data-model-only representation of a manually entered, observed shot
(`ShotRecord`), attachable to a `Player` via `Player.shot_history`. No
fitting/derivation of `CarryDistribution`/`DirectionalDispersion` from
history, no storage technology, no round-level strategy/simulation.

## Architect input

CaddAI Architect reviewed the design: **no ADR required**.

- `ShotRecord` lives in `src/caddai/player/models.py`, not
  `caddai.statistics.models` — `statistics` is a leaf module (enforced by
  `test_architecture_boundaries.py`) with zero `caddai.*` dependencies;
  putting a club-referencing model there would invert/cycle the existing
  `player → statistics` dependency direction.
- The club reference is a plain `club_name: str` snapshot, not an embedded
  `Club` object and not a `ClubCategory`. A `ClubCategory` is too coarse
  (many clubs can share a category). An embedded `Club` reference risks
  either aliasing a mutable object still living in `Player.clubs`, or going
  stale once a club is renamed/removed — undesirable for what should be an
  immutable historical record. `club_name` doesn't need referential
  integrity against current `Player.clubs` for this data-model-only
  milestone (explicitly no aggregation/lookup logic in scope).
- No dependency-direction or module-ownership violation: everything stays
  inside `caddai.player`, already owned by the Player Engineer.
- Keep the `lateral_offset_metres` sign-convention docstring wording
  identical in spirit to `DirectionalDispersion.lateral_bias_metres`
  (negative left / zero on-line / positive right, handedness-independent).
- `achieved_carry_metres` bound is a deliberate domain-modelling choice, not
  a copy-paste of `CarryDistribution.mean_metres`'s `gt=0`: a real observed
  shot can be topped/whiffed and travel a very short but non-negative
  distance, so use `ge=0`, not `gt=0`.
- Keep the optional conditions/date field as free text (`str | None`) — no
  structured `datetime`, to avoid scope creep beyond "data-model-only."
  Field name: `notes` — plain text for conditions and/or date, exactly as
  described in the issue ("optional free-text conditions/date").
- No `frozen=True`/immutability change — stay consistent with existing
  `Club`/`CarryDistribution`/`DirectionalDispersion` style (no frozen
  models yet).
- `Player.shot_history: list[ShotRecord] = Field(default_factory=list)` —
  in-memory only, consistent with the offline-first active-round principle
  already in effect (no network dependency introduced).

## Tasks

### Task 1 — `ShotRecord` model + `Player.shot_history` field

- Owning engineer: Player Engineer
- Files: `src/caddai/player/models.py`, `src/caddai/player/__init__.py`
- Acceptance criteria:
  - New `ShotRecord(BaseModel)`:
    - `club_name: str` (`Field(min_length=1)`, consistent with `Club.name`)
    - `achieved_carry_metres: float` (`Field(ge=0)`)
    - `lateral_offset_metres: float` (unconstrained sign, same convention
      as `DirectionalDispersion.lateral_bias_metres`: negative left, zero
      on-line, positive right, independent of handedness)
    - `notes: str | None = None` (optional free-text conditions/date)
  - `Player.shot_history: list[ShotRecord] = Field(default_factory=list)`
    — defaults to an empty list; existing `Player(...)` call sites across
    the codebase remain valid unchanged (it's optional/defaulted, unlike
    the required `Club.category` precedent in M3.4).
  - `ShotRecord` exported from `caddai.player.__init__.__all__`.
  - No change to `caddai.statistics`, `caddai.strategy`, or any other
    subsystem. No aggregation/fitting logic introduced anywhere.

### Task 2 — Tests for `ShotRecord`/`Player.shot_history`

- Owning engineer: Player Engineer (QA Engineer designs cases first)
- Files: `tests/test_player_models.py`
- Acceptance criteria (from issue + test conventions):
  - Valid construction round-trips all fields, including negative
    (left), zero (on-line), and positive (right) `lateral_offset_metres`.
  - `achieved_carry_metres` boundary: `0.0` is accepted (whiffed/topped
    shot); negative is rejected (`ValidationError`).
  - Empty `club_name` is rejected (`ValidationError`), consistent with
    `Club.name`.
  - `notes` defaults to `None` and an explicit string round-trips.
  - `Player.shot_history` defaults to an empty list when omitted.
  - `Player.shot_history` accepts appended/constructed `ShotRecord`
    entries and preserves order.
  - No test asserts any aggregation/statistics-derivation behaviour (none
    exists) — explicitly out of scope per the issue.

### Task 3 — Documentation update

- Owning engineer: Player Engineer
- Files: `docs/player-model.md`
- Acceptance criteria:
  - Status note updated to describe `ShotRecord` and `Player.shot_history`,
    explicitly noting it remains in-memory only and that no derivation of
    `CarryDistribution`/`DirectionalDispersion` from history exists yet
    (deferred to a future round-history/learning milestone).

## Parallelism

Single owner (Player Engineer) for all tasks; small enough to implement
together in one pass. No parallel delegation needed.

## Escalations

None — Architect confirmed no ADR required.
