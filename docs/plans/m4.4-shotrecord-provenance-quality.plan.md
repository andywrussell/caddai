## Architect review outcome (round 1 — superseded, see round 2 below)

The CaddAI Architect's first read-only review (before PR #63's first
commit) recommended keeping `achieved_carry_metres` required/unchanged and
adding only `measurement_source`/`measurement_quality` record-level
metadata fields. **This was superseded by the round 2 review below**,
prompted by a product-reality correction: normal on-course CaddAI use
cannot directly observe true carry (the ball's first landing point) — only
shot start/finish position, from which total/downrange distance and
finishing lateral offset are derivable. True carry is latent and only
occasionally directly observed (e.g. a launch monitor).

## Architect review outcome (round 2 — binding)

`ShotRecord` records **evidence/observations only**; derived golfer-state
estimates (e.g. carry estimated from total distance) belong in a future,
separate inference step and must never be silently written into
`ShotRecord`'s observed fields. Concretely:

1. **Renamed/re-scoped primary fields:**
   - `total_distance_metres: float = Field(ge=0)` — replaces
     `achieved_carry_metres`; always derivable from observed start/finish
     position, so stays **required**, same as the field it replaces.
   - `lateral_offset_metres: float` — **name unchanged, semantics
     clarified**: now explicitly the lateral offset at the *final resting
     position* (not at carry landing), since only start/finish position is
     directly observable in normal use.
   - `observed_carry_metres: float | None = None` — **new, optional**,
     `ge=0` when present, finite-validated when present. Set **only** when
     a suitable direct-measurement source (e.g. a launch monitor) actually
     measured carry. Never auto-populated from an estimate. Legitimately
     absent for the overwhelming majority of on-course shots.
   - **No cross-field validator enforcing `observed_carry_metres <=
     total_distance_metres`** — `ShotRecord` records evidence, not physics
     consistency; the two can come from independent instruments that may
     legitimately disagree, and rejecting construction on that basis risks
     discarding genuine (if surprising) observations.
2. **Per-quantity measurement metadata, not record-level.** New nested
   submodel:
   ```python
   class ShotMeasurementMetadata(BaseModel):
       source: ShotMeasurementSource = ShotMeasurementSource.UNKNOWN
       quality: ShotMeasurementQuality = ShotMeasurementQuality.UNKNOWN
   ```
   Composed twice:
   - `total_distance_measurement: ShotMeasurementMetadata` — **required**,
     default-constructed (`UNKNOWN`/`UNKNOWN`) since `total_distance_metres`
     is always present.
   - `observed_carry_measurement: ShotMeasurementMetadata | None = None` —
     **optional, paired with `observed_carry_metres`.**
   `ShotMeasurementSource`/`ShotMeasurementQuality` (already added on this
   branch) are reused unchanged for both quantities — no new/renamed
   members needed.
3. **Null-pairing invariant enforced by a `model_validator(mode="after")`:**
   `observed_carry_metres is None` must equal
   `observed_carry_measurement is None`. A structural null-consistency
   check on the type itself (same category as existing finite-value
   validation), not an invented golf business rule.
4. **No new ADR.** `ShotRecord`/`achieved_carry_metres` has no consumer
   outside `caddai.player.models` itself, and PR #63 is unmerged with no
   consumer beyond this same branch — there is no shipped, cross-subsystem
   contract being broken. Call this out explicitly in the PR
   description/CHANGELOG as a deliberate breaking rename of an
   **unreleased** field, for auditability. **ADR 0006 is unaffected** —
   it governs `PlayerShotDistribution` (the golfer's intrinsic *forward*
   shot-production model), not `ShotRecord` (the *observation* type). Two
   pipelines stay cleanly separated:
   - **Forward** (unaffected): golfer shot-production distribution
     (ADR 0006) → true carry (latent) → environment/rollout physics
     (future) → final position.
   - **Learning** (this issue's concern, not implemented here): observed
     final position (`ShotRecord`) → future context-aware inference
     (rollout/environment/surface model) → estimated latent carry →
     future `PlayerShotDistribution` update.
5. **Putting confirmed non-forcing.** `observed_carry_metres` optional +
   `total_distance_metres` the only required distance quantity means a
   `ClubCategory.PUTTER` shot naturally has `observed_carry_metres=None`
   with no structural pressure to invent a carry concept for putts. No
   putting-specific modelling introduced.
6. **Accepted, documented gaps (not implemented here):** no
   `observed_carry_lateral_metres` counterpart for launch-monitor-style
   carry-landing lateral offset (real launch monitors often report this);
   no carry-from-total estimator; no attempted-but-rejected-measurement
   concept. All recorded in `docs/backlog.md`, not built now.
7. `club_name`, `notes` unaffected.

## Scope for this issue (revised)

**In scope:**

- `ShotMeasurementSource` (`MEASURED`, `GPS_ESTIMATE`, `MANUAL_ESTIMATE`,
  `UNKNOWN` default) and `ShotMeasurementQuality` (`UNKNOWN` default,
  `LOW`, `MODERATE`, `HIGH`) enums — unchanged from round 1.
- New `ShotMeasurementMetadata` submodel (`source`, `quality`).
- `ShotRecord` primary fields: `total_distance_metres` (required, renamed
  from `achieved_carry_metres`), `lateral_offset_metres` (unchanged name,
  clarified semantics), `observed_carry_metres` (new, optional),
  `total_distance_measurement` (required metadata),
  `observed_carry_measurement` (optional metadata, null-paired with
  `observed_carry_metres`), `notes` (unchanged).
- Null-pairing validator between `observed_carry_metres` and
  `observed_carry_measurement`.
- `ShotMeasurementMetadata` exported from `caddai.player.__init__.__all__`
  alongside the existing/renamed exports.
- Docstrings explaining observed-vs-latent-carry, the forward/learning
  pipeline split, and that nothing here feeds
  `PlayerShotDistribution`/`CarryDistribution`/`DirectionalDispersion` math.
- Tests fully rewritten for the new shape (see QA task below).
- `docs/player-model.md` status update describing the corrected shape.
- `docs/backlog.md`: replace the now-superseded "should
  `achieved_carry_metres` become optional" item with the accepted gaps
  from Architect point 6 above, plus the still-deferred lie/context,
  penalty/OB, and intended-shot items from round 1.
- `CHANGELOG.md`: revise the `[Unreleased]` entry to describe the final
  (round 2) shape, noting the field rename is a deliberate correction to
  an unreleased field, not a preserved-compatibility change.

**Explicitly out of scope (deferred, tracked in `docs/backlog.md`):**

- Carry-from-total estimation, rollout physics, environment modelling,
  surface/firmness modelling, lie effects.
- A player-domain lie/context type.
- A penalty/OB/lost-ball outcome flag.
- Intended-shot-type/target-line context.
- `observed_carry_lateral_metres` (carry-landing lateral offset).
- Any distribution updating, partial pooling, statistical fitting, outlier
  removal, simulation, strategy, environment physics, persistence, or GPS
  acquisition (M4.5+ and beyond).
