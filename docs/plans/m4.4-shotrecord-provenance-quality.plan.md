## Architect review outcome

The CaddAI Architect reviewed this issue (read-only, no code) and gave a
decisive recommendation, summarised here (full record kept in this
session's log):

1. **`achieved_carry_metres` stays required, unchanged.** Do not add
   `achieved_total_metres` in this issue — carry-vs-total is a new
   measurement axis, not provenance/quality metadata, and is not requested
   by #52's acceptance criteria. Defer to a follow-up issue.
2. **New, `ShotRecord`-specific enum for measurement source** (not reuse of
   `CarryProvenance`) — onboarding provenance describes trust in a one-off
   cold-start self-report; historical-shot measurement provenance is a
   different concept (needs `UNKNOWN`/launch-monitor-style `MEASURED`,
   which `CarryProvenance` doesn't cleanly cover). Reusing it would also
   create an unwanted `models.py → onboarding.py` dependency.
3. **Measurement quality is a separate categorical field**, independent of
   (not derived from) measurement source — two `MEASURED` shots can still
   differ in quality. Default `UNKNOWN`, never a falsely-good default.
4. **Lie/context enum: deferred**, not part of #52's scope; flagged as
   follow-up work (including the open question of whether it should be a
   shared neutral type vs. duplicating `caddai.strategy.LieType`'s
   members).
5. **Penalty/OB/lost-ball flag: deferred**, no consumer yet, not requested
   by #52.
6. **Intended-shot-type/target-line context: deferred**, no consumer yet.
7. **`club_name` string-snapshot limitation: documented only**, no
   redesign (already tracked in `docs/backlog.md`).
8. **No new ADR required** — ordinary additive domain evolution,
   consistent with how M4.3's onboarding enums were added.

## Scope for this issue

**In scope:**

- Two new `StrEnum` types in `src/caddai/player/models.py`:
  - `ShotMeasurementSource`: `MEASURED`, `GPS_ESTIMATE`, `MANUAL_ESTIMATE`,
    `UNKNOWN` (default).
  - `ShotMeasurementQuality`: `UNKNOWN` (default), `LOW`, `MODERATE`,
    `HIGH`.
- `ShotRecord` gains two additive fields with truthful "not assessed"
  defaults:
  - `measurement_source: ShotMeasurementSource = ShotMeasurementSource.UNKNOWN`
  - `measurement_quality: ShotMeasurementQuality = ShotMeasurementQuality.UNKNOWN`
- Both new enums exported from `caddai.player.__init__.__all__`.
- Docstring updates on `ShotRecord` clarifying the observed-vs-estimated
  distinction the new fields exist to support, and that neither field
  feeds `PlayerShotDistribution`/`CarryDistribution`/`DirectionalDispersion`
  math in this issue (that's for M4.5 to decide).
- No behavioural change to existing fields: `club_name`,
  `achieved_carry_metres`, `lateral_offset_metres`, `notes` unchanged in
  type, requiredness, or validation.
- Tests: construction with/without new fields (backward compatible),
  every enum member accepted, invalid enum values rejected, serialization
  (`model_dump`) includes new fields with correct defaults, finite-value
  validation on existing fields unaffected, no new outlier/severe-miss
  rejection introduced (large values still accepted), architecture
  boundary test file needs no changes (no new imports).
- `docs/player-model.md` status update describing the new fields.
- `docs/backlog.md`: record the deferred follow-ups the Architect
  identified (carry-vs-total distinction / optional carry, lie/context
  field, penalty/OB/lost-ball flag, intended-shot context) as explicit
  candidate items, so they are not silently lost.
- `CHANGELOG.md` entry under `[Unreleased]`.

**Explicitly out of scope (deferred, tracked in `docs/backlog.md`):**

- Making `achieved_carry_metres` optional or adding
  `achieved_total_metres`.
- A player-domain lie/context type.
- A penalty/OB/lost-ball outcome flag.
- Intended-shot-type/target-line context.
- Any distribution updating, partial pooling, statistical fitting, outlier
  removal, simulation, strategy, environment physics, persistence, or GPS
  acquisition (M4.5+ and beyond).
