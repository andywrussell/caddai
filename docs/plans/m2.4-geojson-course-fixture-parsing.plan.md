# M2.4 — Local GeoJSON course fixture parsing

GitHub issue: [#6](https://github.com/andywrussell/caddai/issues/6)

## Goal

Define the `caddai`-specific GeoJSON `properties` schema and implement a
loader in `src/caddai/course/` converting a GeoJSON `FeatureCollection` into
the M2.3 `Course`/`Hole`/`Feature` domain models, with a documented sample
fixture and clear validation errors for malformed input.

## Architect input

The CaddAI Architect reviewed this issue (read-only) and recommended:

- New module: `src/caddai/course/geojson.py`, owned by Course Engineer,
  within the existing `course` subsystem. Add it to
  `SUBSYSTEM_BOUNDARIES` in `tests/test_architecture_boundaries.py` with
  `allowed_caddai_prefixes=("caddai.course", "caddai.gps")` (same as the
  existing `course` entry).
- Schema: a `FeatureCollection` with a top-level
  `properties: {"name": <course name>, "holes": [{"number": <int>, "par": <int>}, ...]}`
  course-metadata block, and per-feature (GeoJSON `Point`)
  `properties: {"hole": <int>, "feature_type": "<FeatureType value>"}`.
  `par` lives once per hole in the top-level metadata (single source of
  truth), not repeated/duplicated across every point feature on that hole.
  `Course.name` has no natural per-feature home, so it lives at the
  top-level `properties` only.
- Use plain `json` (stdlib) + manual `[longitude, latitude]` → `Coordinate`
  extraction — **not** `shapely.geometry.shape`. No geometric operation is
  performed on these points; ADR 0002 already rejected using Shapely for
  point-only math (`gps.projection`), and this is the same situation.
  GeoJSON coordinate order is `[longitude, latitude]` — this must be
  mapped explicitly to `Coordinate(latitude=..., longitude=...)`, and is a
  good explicit regression test case.
- Validation approach: small intermediate Pydantic models for the GeoJSON
  `properties` shapes (letting Pydantic validate `feature_type` against
  the `FeatureType` enum for a clear `ValidationError` on unknown types
  "for free"), plus `ValueError` raised directly by the loader for
  structural problems that aren't simple field validation: missing
  `properties` entirely, unsupported `geometry.type` (only `"Point"` is
  supported), a feature's `hole` not present in the top-level `holes`
  metadata, wrong `type` discriminators. No custom exception hierarchy —
  YAGNI; nothing today needs to catch GeoJSON errors distinctly from other
  `ValueError`/`ValidationError`s.
- No ADR required: no new dependency (Shapely already approved but not
  newly invoked; `json` is stdlib), no public API contract (no `api`/`cli`
  exists yet), no canonical unit change, no module ownership change, no
  dependency direction change (`course → gps` already established in
  M2.3).
- Fixture: `tests/fixtures/sample_course.geojson` (new `fixtures/`
  subdirectory under `tests/`), loaded via a path relative to the test
  file.
- Update `docs/course-engine.md`'s "Data format (planned)" section with
  the concrete schema above, and its status header note (mirroring the
  M2.1/M2.3 "now implemented" pattern), once implemented.

## Tasks

1. **Course Engineer** — implement `src/caddai/course/geojson.py`.
   - Intermediate Pydantic models for the GeoJSON `properties` shapes
     (course-level `name`/`holes` metadata; per-feature `hole`/
     `feature_type`).
   - A `load_course(data: dict[str, object]) -> Course` (or equivalent
     signature agreed during implementation) function that:
     - Validates the top-level object is a `FeatureCollection` with a
       `properties` block containing `name` and `holes` (each with
       `number`/`par`).
     - Iterates GeoJSON `Feature` entries, validates `type == "Feature"`
       and `geometry.type == "Point"`, extracts
       `Coordinate(latitude=coordinates[1], longitude=coordinates[0])`,
       validates `properties.hole`/`properties.feature_type`.
     - Groups features by hole number, cross-checked against the
       top-level `holes` metadata (every feature's hole must exist in the
       metadata; every metadata hole must have at least one feature, per
       `Hole.features` `min_length=1`).
     - Constructs and returns a `Course` from the M2.3 domain models.
     - Raises clear `ValueError`/`ValidationError` for: missing hole
       number, unknown feature type, missing top-level metadata,
       unsupported geometry type, a feature referencing an undeclared
       hole.
   - Optionally a convenience `load_course_from_file(path: Path) -> Course`
     wrapper (reads + `json.loads` + `load_course`) if useful for the
     round-trip test and future CLI/demo use — Course Engineer's call.
   - Full strict type hints; concise docstrings.
   - No imports from `player`, `strategy`, `statistics`, `simulation`,
     `llm`, `api`, or `cli`.
   - Add `tests/fixtures/sample_course.geojson`: a small, documented
     (comment via an accompanying test docstring, since GeoJSON has no
     native comments) 2-hole fixture course with tee/fairway/green
     features per hole, matching the schema above.
   - Update `docs/course-engine.md` per the Architect's note above.
   - Update `AGENTS.md`/`docs/course-engine.md` cross-references only if
     needed (should already be consistent from M2.3).

2. **QA Engineer** — write `tests/test_course_geojson.py` covering:
   - The documented `tests/fixtures/sample_course.geojson` fixture parses
     into the correct `Course`/`Hole`/`Feature` objects (hole count,
     per-hole par, per-hole feature types/positions, course name).
   - Round-trip: parse the fixture, assert specific expected values
     (not just "it doesn't raise") for at least one feature's
     `Coordinate` (catching a `[lon, lat]`/`[lat, lon]` swap regression).
   - Malformed input raises clear errors, not silent acceptance:
     - A feature missing `properties.hole`.
     - A feature with an unrecognized `feature_type` string.
     - A feature referencing a hole number absent from the top-level
       `holes` metadata.
     - A `FeatureCollection` missing the top-level `properties` block.
     - A feature with a non-`"Point"` `geometry.type` (e.g. `"Polygon"`).
   - Add a `course` `geojson.py` entry (or extend the existing `course`
     boundary's `source_files`) in
     `tests/test_architecture_boundaries.py`'s `SUBSYSTEM_BOUNDARIES`.
