# M3.7 — Extend developer demo for richer player model

GitHub issue: [#31](https://github.com/andywrussell/caddai/issues/31)

## Goal

Update the developer demo (`src/caddai/strategy/demo.py`) to surface the
richer M3 `Club`/`Player` model — club category, expected carry, carry
variability, lateral dispersion, and systematic lateral bias — as
human-readable, informational-only output, without changing
`recommend_club()`'s selection logic.

Note: this issue was previously closed as "completed" with no PR or code
change ever landing (confirmed via `git log` and an unchanged `demo.py`).
Reopened before starting this work.

## Architect input

CaddAI Architect reviewed the design: **no ADR required**.

- No new dependency, no public API/model contract change, no unit change,
  no ownership change. `docs/architecture.md`'s dependency table already
  lists `strategy → player, statistics`; `recommend.py` is untouched, so
  ADR 0001 (deterministic strategy) is unaffected.
- **Owner: Strategy Engineer** (`demo.py` lives in `strategy/`, this is
  presentation code reading already-public `Club`/`Player` fields — no
  Player Engineer involvement needed).
- `build_demo_request()` currently uses `Club.with_expected_carry(...)`,
  which produces degenerate (zero-variance, zero-bias) clubs. To make the
  new dispersion/variability lines print meaningful non-zero values, the
  Strategy Engineer should construct at least one demo `Club` directly
  (`Club(name=..., carry_distribution=CarryDistribution(...),
  dispersion=DirectionalDispersion(...), category=...)`) with realistic
  sample values — still entirely within `demo.py`, no domain-model change.
- **Boundary-test heads-up**: `tests/test_architecture_boundaries.py`
  currently restricts `strategy`'s `allowed_caddai_prefixes` to
  `("caddai.player", "caddai.strategy")` — `caddai.statistics` is not
  listed. If the implementation adds an explicit `from caddai.statistics
  import CarryDistribution, DirectionalDispersion` (likely, for
  constructing realistic demo clubs and/or strict type hints on a
  formatting helper), add `"caddai.statistics"` to that tuple. This is a
  test-guard update, not a real boundary violation — `architecture.md`
  already documents the transitive dependency.
- New output must stay clearly separate from the existing `Reasons:` block
  so it's obvious the dispersion/variability figures are informational
  only and were not used by `recommend_club()`'s decision.

## Tasks

### Task 1 — Extend demo output

- Owning engineer: Strategy Engineer
- Files: `src/caddai/strategy/demo.py`
- Acceptance criteria:
  - `build_demo_request()` still builds a deterministic
    `RecommendationRequest`; at least one demo `Club` is constructed with
    non-degenerate `carry_distribution`/`dispersion` values (direct
    `Club(...)` construction) so new output lines are non-trivial.
  - `recommend_club()` and `RecommendationRequest`/`RecommendationResult`
    are not modified. Selection/confidence/reasons logic is untouched.
  - Printed output gains new, clearly-labelled, informational-only lines
    for the selected club covering: `category`, `expected_carry_metres`,
    `carry_distribution.stddev_metres` (carry variability),
    `dispersion.lateral_stddev_metres` (lateral dispersion), and
    `dispersion.lateral_bias_metres` (systematic lateral bias) — printed
    with a sign/label that preserves the established convention (negative
    = left of target line, positive = right).
  - New section is visually separated from `Reasons:` and labelled (e.g.
    "Player-model context (informational only, not used in selection)")
    so a reader cannot mistake it for input to the decision.
  - Output stays simple/human-readable — no tables, no extra dependencies.

### Task 2 — Test updates

- Owning engineer: Strategy Engineer (QA Engineer designs cases first)
- Files: `tests/test_strategy_demo.py`
- Acceptance criteria (from QA):
  - Existing tests continue to pass unmodified where they assert on
    unrelated output (club name, playing distance, confidence, reasons).
  - New tests assert the printed output contains the real selected club's
    `category.value`, `expected_carry_metres`, carry stddev, lateral
    stddev, and lateral bias — sourced from `recommend_club(build_demo_request())`,
    not hardcoded expected numbers.
  - A test asserts the sign convention is legible in output for a
    non-zero bias value (e.g. contains "left" for negative bias or "right"
    for positive bias, per whatever label format is chosen).
  - `uv run python -m caddai.strategy.demo` runs successfully end to end.
