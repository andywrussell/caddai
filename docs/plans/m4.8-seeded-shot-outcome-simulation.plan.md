# M4.8 — Seeded probabilistic shot-outcome simulation

GitHub issue: [#56](https://github.com/andywrussell/caddai/issues/56)

## Goal

Add seeded, vectorised bivariate Student-t sampling of intrinsic shot
outcomes from a `PlayerShotDistribution` (ADR 0006's exact construction),
composable with M4.7's optional deterministic environment transform. No
course-relative mapping, no expected strokes/Strokes Gained, no risk/reward
strategy, no persistence/API/mobile — all deferred to M5+.

## Architect input

CaddAI Architect reviewed issue #56 (full text in session record;
summarised below). Verdict: buildable within current boundaries, no ADR
required.

- **Module layout**: one new file, `src/caddai/simulation/sampling.py`.
  `models.py`/`environment.py`/`environment_config.py` (M4.7) unchanged.
  `__init__.py` extended to re-export the new public names.
- **Core sampler signature**:
  ```python
  def sample_bivariate_student_t_shot_outcomes(
      distribution: PlayerShotDistribution,
      count: int,
      rng: np.random.Generator,
  ) -> tuple[ShotOutcome, ...]:
  ```
  Name is technique-specific (not a generic `sample_shot_outcomes`) so a
  future alternate technique gets its own name rather than overloading
  this one. `rng: np.random.Generator` is a **required** positional
  parameter — no default, no bare `seed: int` convenience overload (NumPy's
  own `np.random.default_rng(seed)` idiom already covers that one line;
  adding a second way to do it is premature abstraction). No global NumPy
  random state is ever touched.
- **Pluggable technique**: a `Protocol` (`ShotOutcomeSampler`), not an
  enum/registry/plugin framework — `sample_bivariate_student_t_shot_outcomes`
  is documented as the current implementation of that contract. No runtime
  dispatch table; nothing yet consumes multiple techniques interchangeably.
- **Scale-matrix construction (critical correctness point)**:
  ```python
  Sigma = [
      [carry_scale**2, correlation * carry_scale * lateral_scale],
      [correlation * carry_scale * lateral_scale, lateral_scale**2],
  ]
  ```
  built directly from `carry_scale_metres`/`lateral_scale_metres`/
  `correlation` — **never** from `distribution.implied_covariance_metres_sq`
  (that property already applies the `nu/(nu-2)` factor; passing it to
  `multivariate_normal` as `cov=` would double-apply the factor once
  `z / sqrt(w/nu)` is also applied). `mean=[0.0, 0.0]` is passed to
  `multivariate_normal` — `mu = (carry_location_metres, lateral_bias_metres)`
  is added **after** the `z / sqrt(w/nu)` division, per ADR 0006's
  `X = mu + Z / sqrt(W/nu)`.
- **Exact order of operations**:
  ```python
  z = rng.multivariate_normal(mean=[0.0, 0.0], cov=Sigma, size=count)  # (count, 2)
  w = rng.chisquare(df=distribution.degrees_of_freedom, size=count)  # (count,)
  scale = np.sqrt(w / distribution.degrees_of_freedom)  # (count,)
  x = mu + z / scale[:, None]  # (count, 2)
  ```
  **Broadcasting pitfall**: `z / scale` without `[:, None]` is wrong —
  NumPy aligns from the trailing dimension, so `(count, 2) / (count,)`
  either raises (`count != 2`) or, worse, silently cross-divides columns by
  the wrong scalar when `count == 2`. `scale[:, None]` reshapes to
  `(count, 1)` so each row divides by its own scalar. This exact case
  (`count == 2`) must be a named regression test.
- **Output shape**: `tuple[ShotOutcome, ...]`, one per sample
  (`x[:, 0] -> downrange_metres`, `x[:, 1] -> lateral_metres`, each
  converted via `float(...)`). No raw-array-plus-converter split, no new
  `SimulationResult` wrapper. Composition with the optional M4.7 transform
  is a plain caller-side loop over the returned tuple — this module does
  not decide whether/when environment adjustment happens.
- **Result metadata**: none. Entirely caller-owned (sample count is
  `len(result)`; seed/config-version provenance is a decision-journal/
  telemetry concern, explicitly out of scope per the issue).
- **`count` validation**: `count < 1` → `ValueError` (`0` is *not* a
  legitimate empty-result no-op — it's more likely a caller bug than a
  deliberate "simulate nothing" request). No upper-bound guard in V1 (no
  untrusted-input boundary reaches this function yet; that would be an
  `api`/`cli` adapter's future responsibility, not this domain function's).
- **`caddai.player` boundary**: `sampling.py` must not import
  `caddai.player` and must not reimplement `ClubCategorySupportStatus`/
  support-policy logic — it accepts an already-resolved
  `PlayerShotDistribution`, full stop. A `Club`/`Player`-level convenience
  bridging function is explicitly **out of scope** for M4.8 (no real call
  site yet; defer to M5 when `strategy` needs it).
- **Architecture boundary test**: add `sampling.py` to the existing
  `simulation` `SubsystemBoundary.source_files` entry in
  `tests/test_architecture_boundaries.py`
  (`allowed_caddai_prefixes` stays `("caddai.simulation", "caddai.statistics")`
  — unchanged).
- **ADR**: none required — implements ADR 0006's already-binding formula in
  code; no new dependency, no contract change to an existing type, no unit
  change, no ownership/dependency-direction change.
- **Non-positive downrange / extreme outcomes**: no clamping, truncation,
  resampling, or winsorizing anywhere in `sampling.py`. `ShotOutcome`'s
  existing finite-value validation is the only invariant enforced, and a
  negative `downrange_metres` or large-magnitude `lateral_metres` from the
  Student-t heavy tail is intended, evidence-motivated behaviour (ADR
  0006), not a defect. This is distinct from — and must not replicate —
  `environment.py`'s wind-exposure floor, which is a physical-adjustment
  policy belonging only to the (optional) environment-transform stage.
- **Degrees of freedom**: `distribution.degrees_of_freedom` (a `float`) is
  passed unchanged as `df=` to `rng.chisquare` — no recalibration, rounding,
  or integer coercion.
- **Demo script**: out of scope for M4.8 (Orchestrator decision, per
  Architect's non-blocking `NEEDS_DECISION`) — no real `Club`/`Player` call
  site exists yet to demo against meaningfully; revisit once M5 gives the
  pipeline a genuine end-to-end caller.

## Tasks

### Task 1 — Tests (QA Engineer, informs Task 2)

New `tests/test_simulation_sampling.py`. Minimum coverage (from issue
acceptance criteria + Architect design):

- Valid single sample (`count=1`) and valid batch (`count` large, e.g.
  10,000) — shapes/counts correct, all values finite.
- Same seed (same `np.random.default_rng(seed)` construction) + same
  inputs → identical output (element-for-element `ShotOutcome` equality).
- Different seeds → generally different output (not asserting a specific
  inequality relationship beyond "not identical").
- Omitting an explicit seed (two independently-constructed
  `np.random.default_rng()` generators, no seed) → varying output across
  runs.
- No global NumPy random state mutation: `np.random.get_state()` (legacy
  global state) or drawing from `np.random.default_rng()` before/after a
  seeded call is unaffected by a prior sampling call — assert a
  freshly-constructed unseeded `Generator`'s output is not influenced by
  a preceding seeded call using a different `Generator` instance.
- Construction of `PlayerShotDistribution` performs no random work (no RNG
  needed to build the input fixture).
- Configured location (`carry_location_metres`, `lateral_bias_metres`)
  statistically respected: large-`count` sample mean within a tolerant
  band of `mu` (loose tolerance, no exact match).
- Configured positive correlation → positive empirical correlation
  (`numpy.corrcoef` on a large sample); configured negative correlation →
  negative empirical correlation; zero correlation → empirical correlation
  approximately zero (loose tolerance band, not exact).
- Student-t scale-vs-covariance regression test: assert empirical sample
  covariance approximates `distribution.implied_covariance_metres_sq`
  (the `nu/(nu-2) * Sigma` factor), **not** the raw `Sigma` scale matrix —
  this is the test that would catch a double-applied or missing `nu/(nu-2)`
  factor bug.
- Degrees of freedom preserved: no assertion that changes `nu`; a
  qualitative heavier-tails-than-Gaussian check using a robust statistic
  (e.g. sample kurtosis or a quantile-based tail-weight comparison against
  an equivalent-covariance Gaussian sample) with a generous, non-flaky
  tolerance — or omit if a robust non-flaky formulation isn't achievable,
  per issue guidance ("if there is a robust, non-flaky way").
- The `count == 2` broadcasting-pitfall regression case explicitly (per
  Architect §4b) — verify row `i`'s output uses `scale[i]`, not a
  cross-broadcast value (e.g. by comparing a `count=2` batch draw against
  two independent `count=1` draws from identically-seeded, re-constructed
  generators, expecting the same two `ShotOutcome`s).
- Invalid sample counts: `count=0` and `count=-1` raise `ValueError`;
  `rng.chisquare`/`multivariate_normal` are never reached for invalid
  counts (no partial side effects).
- Non-positive downrange samples retained (not rejected/clamped/resampled):
  construct a distribution/seed combination (or directly assert over a
  large sample) that some samples have `downrange_metres <= 0`, and that
  they appear unchanged in the returned tuple.
- Extreme outcomes not filtered: with a low `degrees_of_freedom` (heavy
  tails) and a large sample, assert at least one outcome exceeds several
  multiples of the implied stddev, and it is present in the output
  (nothing removes statistical outliers).
- Intrinsic outcomes unmodified by environment transform: sample intrinsic
  outcomes, apply `apply_environment_transform` to a copy in a loop, assert
  the original intrinsic tuple's `ShotOutcome` objects are unchanged
  (immutability) and distinct from the adjusted ones when environment
  inputs are non-default.
- Optional-environment path and no-environment path both produce valid,
  usable `ShotOutcome` sequences (composition test: intrinsic sampling +
  caller-side `apply_environment_transform` loop vs. intrinsic sampling
  alone).
- Headwind/tailwind/crosswind integration through M4.7: sample intrinsic
  outcomes with a fixed seed, apply `apply_environment_transform` with
  headwind/tailwind/crosswind `EnvironmentInput`s, and assert the same
  directional effects M4.7's own tests already assert (regression coverage
  at the integration seam, not re-deriving M4.7's formulas).
- Deterministic environment given same intrinsic samples: applying
  `apply_environment_transform` twice to the same intrinsic `ShotOutcome`/
  `EnvironmentInput` pair produces identical results (already covered by
  M4.7, re-asserted here at the composed-pipeline level as a lightweight
  regression check).
- Architecture-boundary preservation: covered by
  `tests/test_architecture_boundaries.py`'s updated `simulation` entry
  (parametrized, no separate test file needed for this part).
