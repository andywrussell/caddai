# M5.0 — Course-relative golf state + expected-strokes research/design spike

## Goal

Resolve the two highest-uncertainty domain-semantics questions blocking M5
implementation, mirroring M4.0's format and rigour, before any M5
implementation issue is opened:

1. **Course-relative outcome semantics.** How an M4 golfer-relative
   `ShotOutcome` (signed downrange/lateral distance relative to the
   golfer's selected target line) becomes a course-relative resulting
   state, using existing `course` geometry.
2. **Minimal `GolfState`.** The smallest state representation the future
   expected-strokes/Strokes Gained/strategy layer needs, its canonical
   owning module (explicitly unresolved per the M5 roadmap entry and issue
   #11), and the ownership of the classification operation that produces
   it.
3. **Expected-strokes V0 evidence review.** A genuine evidence review
   (sources, populations, applicability, licensing) of what a defensible,
   offline-compatible expected-strokes-to-hole-out model could look like
   for CaddAI, without committing to an implementation.

This is a **research/design spike only**. No `GolfState`, course-relative
classification, rollout physics, expected strokes, Strokes Gained, strategy
utility, round lifecycle, WHS calculation, synthetic harness, or M6
production-runtime work is implemented. No detailed M5 implementation issue
tree is created. The task ends with two explicit human decision gates
(`GolfState` architecture, expected-strokes V0), not an automatic transition
to implementation — this mirrors how M4.0 gated the rest of M4
(`docs/plans/m4-roadmap-redefinition.plan.md`).

## Architect input

The CaddAI Architect subagent reviewed the design space (dependency graph,
`GolfState` ownership options, course-relative classification ownership,
ADR triggers) before the research document was drafted. Its findings are
folded directly into the research document under "GolfState ownership
options" and "Course-relative classification ownership" — see
[docs/research/m5-golf-state-expected-strokes.md](../research/m5-golf-state-expected-strokes.md).
No ADR is authored by this task itself; the research document explicitly
flags which future ADRs are *likely* once a `GolfState`/expected-strokes
design is actually approved and implemented (a new foundational module
and/or a new public contract are both plausible ADR triggers per
`AGENTS.md` §13), consistent with how ADR 0006/0007 were only written once
M4.0's conclusions were reviewed and accepted.

## Known tooling limitation (external research) — superseded by amendment

The original spike session had no live web-fetch/browsing tool available,
so its expected-strokes evidence review was built from unverified general
knowledge rather than freshly fetched sources, unlike M4.0's research
document. A follow-up amendment (dated 2026-09-01, same branch/PR)
performed live web research with a fetch tool available, verified eight
external sources (Broadie 2011/2008, Golfmetrics, DataGolf, Arccos, Shot
Scope, the Padova thesis, and Wikipedia's WHS summary), and narrowed the
decision gate accordingly: the semantic/conditioning concept (distance +
lie + ability-conditioned expected strokes) is now well-supported by
verified evidence, but no usable public numeric baseline was found, so the
monotonic-interpolation-plus-handicap-band model is recorded as a leading
engineering candidate for the contract shape only, not an approved V0. See
[docs/research/m5-golf-state-expected-strokes.md](../research/m5-golf-state-expected-strokes.md)
for the full verified evidence package and updated decision gates.

## Tasks

1. **Architect design review** (CaddAI Architect, read-only) — `GolfState`
   ownership options (>=3), course-relative classification ownership,
   dependency-direction analysis, ADR-trigger assessment. No file edits.
2. **Research/design document** (Strategy Engineer) —
   `docs/research/m5-golf-state-expected-strokes.md`, covering all required
   sections (current-state audit, course-relative transformation,
   `GolfState` requirements/ownership, terrain/rollout V0, expected-strokes
   evidence/options/recommendation, data/licensing table, putting/penalty/
   recovery treatment, provisionality, performance/batch implications, edge
   cases, ADR requirements, deferred work) plus the two decision gates.
   Reads Architect's findings from Task 1, `AGENTS.md`, and the docs/ADRs
   listed in the originating request. No production code changes.
3. **QA review** (QA Engineer) — reviews the proposed `GolfState` for
   testability, missing invariants, and missing edge cases; does not write
   or change implementation, and does not need to write executable tests
   for a spike with no implementation, but should record concrete future
   acceptance-criteria-shaped test ideas in the document's own edge-case
   section if gaps are found.
4. **Adversarial review** (Adversarial Reviewer, read-only) — checks the
   research document for unjustified precision, silently-invented Rules-
   of-Golf/WHS logic, ADR-trigger blind spots, and dependency-direction
   mistakes. Returns `APPROVE` or `REQUEST_CHANGES`.
5. **Integrator** — quality gate (docs-only change: format/lint/type/test
   still run to confirm nothing else broke), `CHANGELOG.md` entry, commit,
   push, open a **draft** PR. No merge.

## Parallelism

Tasks are sequential (each depends on the previous one's output); no two
agents edit the research document concurrently.
