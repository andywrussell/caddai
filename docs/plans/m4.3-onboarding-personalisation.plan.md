# M4.3 — Onboarding personalisation of `PlayerShotDistribution`

GitHub issue: [#51](https://github.com/andywrussell/caddai/issues/51)

## Goal

Initialise a golfer-specific `PlayerShotDistribution` for a given club from
`resolve_population_prior` (ADR 0007) output plus onboarding information
(handicap, club/`ClubCategory`, self-reported carry + provenance, common
miss, shot shape) — the cold-start step in
`docs/research/m4-probabilistic-golfer-model.md`'s "Cold-start
initialization and personal learning" section. No `ShotRecord` learning, no
partial pooling, no environment/physics, no Monte Carlo, no strategy, no
course-relative mapping, no ML.

## Architect input

CaddAI Architect reviewed the issue, ADR 0006, ADR 0007, the M4.0 research
document, current `caddai.statistics`/`caddai.player`, and
`tests/test_architecture_boundaries.py`. Summary of decisions (full review
retained in session record):

1. **Location:** new `src/caddai/player/onboarding.py`, composing
   `caddai.statistics.resolve_population_prior`/`PlayerShotDistribution`.
   Fits the existing, approved `caddai.player -> caddai.statistics` edge.
   `caddai.statistics` remains untouched/leaf.
2. **Carry provenance:** a new `caddai.player` enum (`CarryProvenance`:
   `MEASURED` / `GPS_ESTIMATE` / `PERSONAL_ESTIMATE`), distinct from
   `caddai.statistics.population_prior.PopulationPriorConfidence`/
   `PopulationPriorProvenance` (different semantic axis — quality of a
   golfer's self-report, not where a population-prior config cell came
   from). A private mapping derives a qualitative confidence
   (LOW/MODERATE/HIGH shape) from provenance; this confidence is
   **metadata only** — never fed into `carry_scale_metres` or any other
   `PlayerShotDistribution` scale/correlation/dof field. This is the
   mechanical enforcement of the aleatoric/epistemic separation the issue
   requires.
3. **Return type:** a small additive result type,
   `OnboardingPersonalisationResult` (`shot_distribution:
   PlayerShotDistribution`, `carry_provenance: CarryProvenance`,
   `carry_confidence: CarryConfidence`, `population_prior:
   PopulationPriorResult`), not new fields bolted onto
   `PlayerShotDistribution` itself. Precedented by `PopulationPriorResult`
   in M4.2 under ADR 0007's "adjacent type" allowance — not a new
   architectural pattern needing its own ADR.
4. **Common-miss bias magnitude:** a single, explicitly named/versioned
   provisional constant in `caddai.player.onboarding`
   (`ONBOARDING_COMMON_MISS_BIAS_METRES`, with an
   `ONBOARDING_CONFIG_VERSION` string), applied only via the **sign**
   derived from a `CommonMiss` enum (`LEFT`/`NONE`/`RIGHT`) — never a
   magnitude derived from handicap/club/anything else.
5. **ADR impact: none.** Not a public API contract change to
   `PlayerShotDistribution` (untouched); the adjacent-result-type pattern
   and provisional-numeric-constant pattern are both already sanctioned by
   ADR 0006/0007 without requiring a new ADR for each application.
6. **Ownership:** Player Engineer; no cross-agent coordination required
   provided `caddai/statistics/**` is not modified.
7. **Other:**
   - `tests/test_architecture_boundaries.py`'s `player`
     `SubsystemBoundary.source_files` tuple must be updated to include the
     new `onboarding.py` file, or its imports go unchecked.
   - `PUTTER`/`OTHER` handling: call `resolve_population_prior` first and
     let `PopulationPriorUnsupportedCategoryError` (existing `status`
     attribute) propagate unmodified — no new onboarding-specific error
     type, no swallowing.
   - `common_miss` accepted as a discrete enum (`LEFT`/`NONE`/`RIGHT`), not
     a raw signed float — sign convention applied internally.
   - `shot_shape` stored on the input/result for future use; read by
     nothing in this issue's bias logic.

No `NEEDS_DECISION` escalation raised.

## Tasks

### Task 1 — `caddai.player.onboarding` implementation (Player Engineer)

Files: `src/caddai/player/onboarding.py` (new),
`src/caddai/player/__init__.py` (export new public names).

- `CarryProvenance` (StrEnum): `MEASURED`, `GPS_ESTIMATE`,
  `PERSONAL_ESTIMATE`.
- `CarryConfidence` (StrEnum): `LOW`, `MODERATE`, `HIGH` — derived from
  `CarryProvenance` via a private mapping (not user-supplied).
- `ShotShape` (StrEnum): `STRAIGHT`, `DRAW`, `FADE` — recorded, not
  consumed by bias logic in this issue.
- `CommonMiss` (StrEnum): `LEFT`, `NONE`, `RIGHT` — sign-only input,
  matching the existing lateral sign convention (negative left, zero
  on-line, positive right).
- `ONBOARDING_CONFIG_VERSION` (str) and
  `ONBOARDING_COMMON_MISS_BIAS_METRES` (float, provisional, documented as
  arbitrary/unvalidated pending calibration) module-level constants.
- `OnboardingPersonalisationResult` (Pydantic `BaseModel`):
  `shot_distribution: PlayerShotDistribution`,
  `carry_provenance: CarryProvenance`, `carry_confidence: CarryConfidence`,
  `population_prior: PopulationPriorResult`.
- `personalise_shot_distribution(*, handicap_index, club_category,
  reported_carry_metres, carry_provenance, common_miss, shot_shape=
  ShotShape.STRAIGHT) -> OnboardingPersonalisationResult`:
  - Validate `reported_carry_metres` finite and > 0 at this boundary
    (raise `ValueError` — matches `caddai.course.distance`/
    `resolve_population_prior` plain-function precedent).
  - Call `resolve_population_prior(handicap_index, club_category)` —
    propagate `PopulationPriorUnsupportedCategoryError`/`ValueError`
    unmodified for invalid handicap or unsupported category (PUTTER/OTHER).
  - Build `PlayerShotDistribution`:
    - `carry_location_metres = reported_carry_metres` (strongly anchors
      location per the issue/research doc — no invented trust-weighted
      blend since no defensible population carry-location prior exists to
      blend toward).
    - `lateral_bias_metres = ONBOARDING_COMMON_MISS_BIAS_METRES *
      sign(common_miss)` (`LEFT` -> -1, `NONE` -> 0, `RIGHT` -> +1).
    - `carry_scale_metres`, `lateral_scale_metres`, `correlation`,
      `degrees_of_freedom` copied directly from
      `population_prior.parameters` — untouched by carry provenance.
    - `family` from `population_prior.parameters.family`.
  - Derive `carry_confidence` from `carry_provenance` via the private
    mapping (`MEASURED` -> `HIGH`, `GPS_ESTIMATE` -> `MODERATE`,
    `PERSONAL_ESTIMATE` -> `LOW`).
  - No RNG, no sampling, no side effects.

### Task 3 — Tests (QA Engineer)

New file `tests/test_player_onboarding.py` covering at minimum:

- Valid cold-start construction for a supported club category.
- Continuous handicap flows through to `resolve_population_prior`
  (no private `_HandicapBand` dependency).
- Reported carry (any plausible unit input already in metres per
  `AGENTS.md` §5) is used directly as `carry_location_metres`.
- `common_miss=LEFT` -> negative `lateral_bias_metres`; `RIGHT` -> positive;
  `NONE` -> zero.
- `shot_shape` (`DRAW`/`FADE`/`STRAIGHT`) does not change
  `lateral_bias_metres` for otherwise-identical inputs.
- `carry_provenance` distinctions: `MEASURED`/`GPS_ESTIMATE`/
  `PERSONAL_ESTIMATE` map to distinct `carry_confidence` values, and
  **do not** change `carry_scale_metres`/`lateral_scale_metres`/
  `correlation`/`degrees_of_freedom` for otherwise-identical inputs
  (mechanical proof of the aleatoric/epistemic separation).
- `ClubCategory.PUTTER` -> `PopulationPriorUnsupportedCategoryError` with
  `status=DEFERRED` propagates.
- `ClubCategory.OTHER` -> same error with `status=NOT_MODELABLE` propagates.
- Invalid/non-finite `reported_carry_metres` (<=0, NaN, +/-inf) raises
  `ValueError`.
- Invalid/non-finite `handicap_index` propagates `resolve_population_prior`'s
  existing `ValueError`.
- No randomness: two calls with identical inputs produce identical output.
- `tests/test_architecture_boundaries.py` still passes with `onboarding.py`
  added.
