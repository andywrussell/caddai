# M3.3 — Evolve Club/Player to carry distribution + dispersion

GitHub issue: [#28](https://github.com/andywrussell/caddai/issues/28)

## Goal

Evolve `Club` (`src/caddai/player/models.py`) to carry a `CarryDistribution`
and `DirectionalDispersion` (from `caddai.statistics`) instead of a bare
scalar `expected_carry_metres`, without breaking
`caddai.strategy.recommend.recommend_club()`. Depends on M3.1 (#26) and
M3.2 (#27), both already merged. Blocks M3.5 (performance-history data
model) and M3.7 (developer demo update).

## Architect input

CaddAI Architect reviewed the design: **no ADR required**.

- `Club`/`Player` are a documented, evolving M1 placeholder
  (`docs/player-model.md` already flags `expected_carry_metres` as "a
  single scalar... placeholder, not a distribution"), and the M3.1 plan
  explicitly pre-committed this reconciliation to M3.3. This is execution
  of an already-agreed plan, not a novel architectural decision.
- Making `expected_carry_metres` a read-only `@computed_field` (rather than
  a settable constructor kwarg) is a narrowing of a pre-1.0, single-owner,
  internal domain model's constructor surface, not a stable external
  contract break — no `api`/`cli` adapter exists yet to be affected.
- `player` → `caddai.statistics` matches the dependency table in
  `AGENTS.md` §3 and `docs/architecture.md`'s dependency graph exactly.

Guidance incorporated into the tasks below:

- **Drop `category`** from `with_expected_carry(...)`'s signature. No
  `category`/club-type concept exists anywhere in the domain model today;
  inventing one as a side effect of this issue is scope creep. A future
  `ClubCategory` concept, if wanted, gets its own small issue.
- Default/degenerate distribution and dispersion for
  `with_expected_carry(...)`:
  `CarryDistribution(mean_metres=expected_carry_metres, stddev_metres=0.0)`
  and `DirectionalDispersion(lateral_stddev_metres=0.0,
  lateral_bias_metres=0.0)` — both zero values are already documented,
  tested, valid "no measured variability/spread yet" states from M3.1/M3.2,
  not physically nonsensical. Docstring must call this out explicitly as a
  placeholder/degenerate (point-mass) distribution so future M4 Monte Carlo
  work doesn't mistake it for "measured, genuinely zero-dispersion."
- Field names must be exactly `carry_distribution: CarryDistribution` and
  `dispersion: DirectionalDispersion`.
- Use Pydantic v2 `@computed_field` + `@property` for
  `expected_carry_metres`, verified under `mypy --strict`.
- **NaN/Infinity validation consistency across `CarryDistribution` and
  `DirectionalDispersion` is explicitly out of scope for this issue.**
  Rationale (Architect): #28's goal is composition, not hardening
  already-shipped M3.1/M3.2 validation; the defaults this issue introduces
  are all finite so #28's correctness doesn't depend on it; it matters
  before M4 (Monte Carlo) starts sampling these values, not before #28
  merges. **Follow-up action:** file a new backlog/GitHub issue — "Reject
  NaN/Infinity across `statistics` models" — scoped to
  `src/caddai/statistics/models.py`, to land before M4 begins.
- Watch for indirect test breakage: any test asserting via
  `model_dump()`/serialized-dict comparison (rather than direct attribute
  access) may need updating because `expected_carry_metres` moves from a
  stored field to a computed one.

## Tasks

### Task 1 — `Club` composition + computed field + convenience constructor

- Owning engineer: Player Engineer
- Files: `src/caddai/player/models.py`
- Acceptance criteria:
  - `Club` gains `carry_distribution: CarryDistribution` and
    `dispersion: DirectionalDispersion` required fields.
  - `Club.expected_carry_metres` becomes a `@computed_field` `@property`
    returning `self.carry_distribution.mean_metres` — no stored field of
    that name remains.
  - `Club.with_expected_carry(name: str, expected_carry_metres: float) ->
    Club` classmethod builds a degenerate `CarryDistribution` (stddev 0.0)
    and `DirectionalDispersion` (stddev 0.0, bias 0.0) from a bare
    expected-carry scalar. No `category` parameter.
  - `Player` model unchanged (still `name`, `clubs`).
  - `recommend.py` is not modified and continues to pass unchanged.

### Task 2 — Test updates for the new `Club` shape

- Owning engineer: Player Engineer (QA Engineer designs cases first)
- Files: `tests/test_player_models.py`, `tests/test_strategy_recommend.py`,
  `tests/test_strategy_demo.py`
- Acceptance criteria (from issue + QA):
  - Existing `Club(name=..., expected_carry_metres=...)` call sites in
    `test_strategy_recommend.py`/`test_strategy_demo.py` (and
    `src/caddai/strategy/demo.py`) become
    `Club.with_expected_carry(name=..., expected_carry_metres=...)`, with
    no other change to those files' logic/assertions.
  - `test_player_models.py` covers: constructing `Club` directly with
    explicit `carry_distribution`/`dispersion`; `expected_carry_metres`
    correctly reflects `carry_distribution.mean_metres` (including when it
    differs from any prior bare-scalar-style expectations); rejecting a
    missing `carry_distribution`/`dispersion`; `with_expected_carry(...)`
    produces a degenerate distribution/dispersion (`stddev_metres == 0.0`,
    `lateral_stddev_metres == 0.0`, `lateral_bias_metres == 0.0`) and a
    matching `expected_carry_metres`.
  - `recommend_club()` behaviour (club selection, confidence, reasons) is
    unchanged for equivalent inputs — existing `test_strategy_recommend.py`
    assertions pass unmodified except at `Club(...)` construction call
    sites.
  - `strategy/demo.py` unchanged except at its `Club(...)` construction
    call sites.
