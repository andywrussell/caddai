# M2.4.5 — Polygon/boundary course geometry and GeoJSON Polygon support

GitHub issue: [#22](https://github.com/andywrussell/caddai/issues/22)

## Goal

Extend `caddai.course`'s domain models and GeoJSON parsing to represent
polygon/boundary geometry for course features (e.g. greens, hazards), so
that M2.5's distance-to-feature queries (issue #7 — green front/centre/back,
hazard carry along a line of play) have real boundary geometry to query
against, instead of only single-point features.

## Architect input

The CaddAI Architect reviewed this issue (read-only) and recommended:

- Keep `Feature.position: Coordinate` required (backward-compatible with
  existing point-only features) and add an optional
  `boundary: tuple[Coordinate, ...] | None` field for an exterior polygon
  ring, rather than a discriminated point/polygon union — lower churn, no
  type-narrowing required of future consumers.
- **Required change from the initial proposal**: enforce, not just
  document by convention, that `position` equals `boundary`'s centroid when
  `boundary` is present. Add a Pydantic `model_validator` on `Feature`
  itself (not only in the GeoJSON loader) so any direct construction of an
  inconsistent `Feature` fails loudly. Document that a polygon's centroid
  is a convenience representative point only (not guaranteed inside a
  concave polygon), and is not a stand-in for "front/centre/back"
  semantics — that's M2.5's job.
- No restriction on which `FeatureType`s may carry a `boundary` — the
  issue's "e.g. green, bunker, water" is illustrative, not exhaustive;
  encoding a business restriction into the domain model now would be
  premature.
- Accept a single exterior ring only for this issue; Polygons with interior
  rings (holes) are explicitly rejected with a distinct, clearly-worded
  `ValueError` — a deliberate, documented non-goal, not a silent gap.
- Validate ring closure (first coordinate == last coordinate) and minimum
  vertex count (≥4 positions = 3 distinct vertices + closing duplicate) as
  GeoJSON-structural concerns in `geojson.py` (`ValueError`, consistent with
  the existing structural/field-level split); validate geometric validity
  (non-self-intersecting, non-degenerate/`area > 0`) and the
  position/boundary centroid invariant as domain-model concerns in
  `models.py` (`ValidationError`, via Pydantic).
- Use a **transient, per-feature, ad hoc local-projection origin** (the
  ring's own first vertex) via `gps.projection.to_local`/`to_coordinate` to
  run Shapely validity/centroid checks, then discard the local
  representation — do **not** invent a durable "course origin"/"hole
  origin" concept in this issue. That decision legitimately belongs to
  M2.5, which knows what shared frame it needs for cross-feature distance
  queries (front/centre/back, hazard-carry lines). This must be recorded in
  the ADR as a deliberate deferral, not an oversight.
- **ADR required**: yes, two independent triggers — (a) a public API/
  contract change (`Feature`'s schema; `load_course`'s accepted GeoJSON
  geometry types and error contract) and (b) the first real activation of
  Shapely, which ADR 0002 explicitly deferred to "when genuinely needed."
  New ADR **0003** (next available number), referencing/extending ADR
  0002 — do not mark 0002 superseded, since its original point-to-point
  decision is unchanged and still correct. The ADR must cover:
  1. The `Feature.boundary` shape and `position`-as-centroid decision,
     including the concave-polygon caveat.
  2. The enforced `position`/`boundary` consistency invariant.
  3. The single-exterior-ring, no-holes scope limitation and its
     `ValueError` contract.
  4. The ring validation contract (closed ring, minimum vertex count,
     `is_valid`/`area > 0` degeneracy checks).
  5. The transient, per-feature ad hoc local-projection origin, explicit
     that a shared local-projection origin is deferred to M2.5.
  6. Confirmation this activates but does not change ADR 0002's decision.
- No dependency-direction, module-ownership, or boundary-test concerns:
  `shapely` is already approved (`AGENTS.md` §9, `pyproject.toml`);
  `tests/test_architecture_boundaries.py`'s `course` boundary only
  restricts `caddai.*` imports, not third-party ones; `course`'s use of
  `gps.projection` stays within its already-allowed
  `("caddai.course", "caddai.gps")` prefixes.

## Tasks

1. **Course Engineer** — `src/caddai/course/models.py`:
   - Add `boundary: tuple[Coordinate, ...] | None = Field(default=None, min_length=3)`
     to `Feature`.
   - Add a small shared helper (module-level, not underscore-private, since
     `geojson.py` reuses it), e.g. `polygon_centroid(boundary: tuple[Coordinate, ...]) -> Coordinate`:
     projects `boundary` vertices to local metres via `gps.projection.to_local`
     using `boundary[0]` as an ad hoc origin, builds a `shapely.geometry.Polygon`,
     and unprojects its centroid back via `gps.projection.to_coordinate`.
   - Add a Pydantic `model_validator(mode="after")` on `Feature` that, when
     `boundary` is not `None`:
     - builds the same local-projection Shapely `Polygon` and rejects
       (`ValueError` → `ValidationError`) an invalid or degenerate
       (`area <= 0`) ring,
     - checks `position` matches `polygon_centroid(boundary)` within a
       0.01 m tolerance (consistent with ADR 0002's stated round-trip
       accuracy) and rejects a mismatch with a clear error message.
   - Update the module docstring to remove "deferred" language and
     describe the new polygon/boundary capability and its limitations
     (single exterior ring only; centroid is a representative point, not
     front/centre/back).

2. **Course Engineer** — `src/caddai/course/geojson.py`:
   - Accept `geometry.type == "Polygon"` in `_parse_feature` (alongside the
     existing `"Point"` handling).
   - Parse `geometry.coordinates`: require exactly one ring (reject
     zero or multiple rings — interior rings/holes — with a distinct
     `ValueError`); require the ring to be closed (first coordinate ==
     last coordinate) and have ≥4 positions, else `ValueError`; extract
     `[longitude, latitude]` pairs into `Coordinate`s (dropping the
     duplicated closing vertex) preserving the existing coordinate-order
     handling/regression-test precedent.
   - Compute `position` via `models.polygon_centroid(boundary)` and
     construct `Feature(feature_type=..., position=..., boundary=...)`
     (letting the model's own validators catch geometric invalidity).
   - Update the module docstring accordingly.

3. **Course Engineer** — fixtures & docs:
   - Extend `tests/fixtures/sample_course.geojson` with at least one green
     polygon and one hazard (bunker or water) polygon feature (in addition
     to existing point features), keeping the fixture documented.
   - Update `docs/course-engine.md`: replace "Shapely polygon geometry and
     hazard carry queries remain planned" language with a description of
     the new capability and its scope limits (single exterior ring; no
     interior rings/holes; `position` is a centroid convenience point).
   - Write ADR `docs/adr/0003-course-boundary-geometry.md` (exact filename
     TBD by Course Engineer) per the Architect's required contents above,
     status `Accepted` (human has approved this direction in this
     conversation), cross-linked from `docs/adr/README.md`'s index and
     `docs/course-engine.md`.

4. **QA Engineer** — `tests/test_course_models.py`:
   - `Feature` accepts a valid `boundary` (≥3 vertices) with a matching
     centroid `position`.
   - `Feature` rejects a `boundary` with fewer than 3 vertices.
   - `Feature` rejects a `position` that does not match `boundary`'s
     centroid (the enforced invariant).
   - `Feature` rejects a self-intersecting/degenerate (zero-area) polygon
     ring.
   - `Feature` without `boundary` behaves exactly as before (regression).

5. **QA Engineer** — `tests/test_course_geojson.py`:
   - Replace/update `test_load_course_rejects_non_point_geometry` (which
     currently asserts a `"Polygon"` geometry.type is rejected) to reflect
     the new contract — a *valid* `Polygon` feature now parses
     successfully; keep a renamed/adjusted test asserting some other
     unsupported `geometry.type` (e.g. `"LineString"`) is still rejected.
   - A valid Polygon feature (documented ring) parses into a `Feature`
     with the expected `boundary` vertices and a `position` matching the
     hand-computed centroid.
   - Degenerate/malformed Polygon cases raise clear errors: ring not
     closed, fewer than 4 positions, zero rings, more than one ring
     (interior ring/hole rejection).
   - The extended fixture's green/hazard polygons parse into the expected
     `Feature`s (hole/feature_type/boundary vertex count).

## Explicit non-goals

- No distance-to-feature query logic (green front/centre/back distance,
  hazard-carry-along-line-of-play) — remains M2.5 (#7)'s scope, now
  unblocked.
- No interior ring (hole-in-polygon) support.
- No durable shared "course origin"/"hole origin" local-projection concept
  — left to M2.5.

## Parallelism

Single subsystem, single owner (Course Engineer) — no parallel engineer
tasks. QA Engineer test design proceeds alongside/ahead of implementation,
both on the same feature branch.

## Escalations

None beyond the ADR already scoped above (human has approved proceeding
with Option B / this design in conversation). No new dependency (Shapely
already approved), no canonical-unit change, no ownership change, no
dependency-direction change.
