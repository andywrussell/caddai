# M3.4 — Club identity and category

GitHub issue: [#29](https://github.com/andywrussell/caddai/issues/29)

## Goal

Add a `ClubCategory` taxonomy and a required `Club.category` field to
`src/caddai/player/models.py`, alongside the existing free-text `name`.
Category is metadata only — no strategy behaviour may key off it in this
change.

## Architect input

CaddAI Architect reviewed the design: **no ADR required**.

- `ClubCategory` values exactly as specified in the issue: `DRIVER`,
  `FAIRWAY_WOOD`, `HYBRID`, `IRON`, `WEDGE`, `PUTTER`, `OTHER` — a stdlib
  `enum.StrEnum`, matching the existing pattern used by `course`/`strategy`
  domain enums.
- `Club.category: ClubCategory` is **required** (no default) — consistent
  with every other domain `StrEnum` field in the codebase (`Wind.direction`,
  `FeatureType`, etc.) and with the M3.3 plan's explicit deferral of
  `category` into "its own small issue." A silent default would undermine
  the taxonomy's purpose since nothing downstream reads it yet to surface
  an omission.
- `Club.with_expected_carry(...)` gains an optional
  `category: ClubCategory = ClubCategory.OTHER` parameter. This keeps the
  method's documented "placeholder/degenerate, no real data yet" philosophy
  consistent (same spirit as its existing `stddev_metres=0.0` defaults) and
  means all existing call sites in `strategy/demo.py`,
  `test_strategy_recommend.py`, and `test_player_models.py` remain valid
  unchanged — zero unnecessary edits outside Player Engineer's owned files.
- `Club` is a documented, evolving, pre-1.0, single-owner internal domain
  model; narrowing its constructor surface is not a stable external API
  break — no `api`/`cli` adapter exists yet to be affected.
- No new dependency, no unit change, no ownership change, no dependency
  direction change, no touch to `caddai.strategy` business logic.
- `ClubCategory` is exported from `caddai.player.__init__` alongside `Club`
  and `Player`.

## Tasks

### Task 1 — `ClubCategory` enum + `Club.category` field

- Owning engineer: Player Engineer
- Files: `src/caddai/player/models.py`, `src/caddai/player/__init__.py`
- Acceptance criteria:
  - New `ClubCategory(StrEnum)` with members `DRIVER`, `FAIRWAY_WOOD`,
    `HYBRID`, `IRON`, `WEDGE`, `PUTTER`, `OTHER`.
  - `Club` gains a required `category: ClubCategory` field. `Club.name`'s
    existing `Field(min_length=1)` validation is unchanged.
  - `Club.with_expected_carry(name, expected_carry_metres, category:
    ClubCategory = ClubCategory.OTHER) -> Club` — existing two positional
    call sites (`with_expected_carry("7 Iron", 140.0)`) continue to work.
  - `ClubCategory` exported from `caddai.player.__init__.__all__`.
  - No change to `caddai.strategy` — category introduces no strategy
    behaviour.

### Task 2 — Tests for `ClubCategory`/`Club.category`

- Owning engineer: Player Engineer (QA Engineer designs cases first)
- Files: `tests/test_player_models.py`
- Acceptance criteria (from issue):
  - Parametrized construction test covering every `ClubCategory` value.
  - A test rejecting an invalid/out-of-enum category string raises
    `ValidationError`.
  - A test confirming `Club.name`'s existing validation (min length 1) is
    unchanged/unaffected by the new field.
  - A test confirming `Club.with_expected_carry(...)` without an explicit
    `category` argument defaults to `ClubCategory.OTHER`, and that passing
    an explicit `category` overrides it.
  - Existing tests in `test_player_models.py`,
    `test_strategy_recommend.py`, and `test_strategy_demo.py` continue to
    pass without modification (verifies the default keeps existing
    `Club(...)`/`with_expected_carry(...)` call sites unaffected — note:
    `test_player_models.py` has direct `Club(...)` constructor call sites
    from M3.3 that will need `category=...` added, since `category` is
    required on the full constructor).

### Task 3 — Documentation update

- Owning engineer: Player Engineer
- Files: `docs/player-model.md`
- Acceptance criteria:
  - Status note updated to describe `ClubCategory` and `Club.category`,
    noting it is metadata only — no strategy behaviour depends on it yet.
