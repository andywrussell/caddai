# M4.2 — `PopulationPrior` population parameter model

GitHub issue: [#50](https://github.com/andywrussell/caddai/issues/50)

## Goal

Define `PopulationPrior`, the replaceable handicap/club-category →
`PlayerShotDistribution`-compatible parameter mapping required by
[ADR 0007](../adr/0007-population-prior-replaceability.md), backed by a
small, explicit, versioned, provisional config table. Migrate `ClubCategory`
from `caddai.player` into `caddai.statistics` to preserve dependency
direction (`caddai.statistics` must remain a leaf module).

No onboarding personalisation, no `ShotRecord` updating, no simulation/
sampling, no environment physics, no strategy, no ML training, no cloud
lookup — those are out of scope (M4.3+).

## Architect input

CaddAI Architect reviewed the issue, ADR 0006/0007, and the M4.0 research
document. **No new ADR required** — internal reorganisation within one
owner's subsystems (Player Engineer owns both `player` and `statistics`),
no dependency-direction change, no public-API break (re-export preserves
`caddai.player.ClubCategory`), no unit/dependency change.

### 1. `ClubCategory` migration

- Canonical definition moves to `src/caddai/statistics/models.py`.

  import ..., ClubCategory` + `__all__`).

  instead of defining it; `Club.category`/`with_expected_carry` unchanged.
- `caddai/player/__init__.py` **still re-exports** `ClubCategory` unchanged
  (`from caddai.player.models import Club, ClubCategory, Player,
  ShotRecord`) — every existing import path and serialized `StrEnum` value
  is preserved.
- `tests/test_architecture_boundaries.py`: no `allowed_caddai_prefixes`
  change needed for either boundary; add the two new statistics files
  (`population_prior.py`, `population_prior_config.py`) to the
  `statistics` boundary's `source_files` tuple.

### 2. `PopulationPrior` domain shape

`PopulationPrior` does **not** return a `PlayerShotDistribution` directly —
it returns a partial parameter bundle. `carry_location_metres`/
`lateral_bias_metres` are not evidence-supportable from handicap +
club-category alone (self-reported carry/common-miss belong to M4.3
onboarding); inventing population defaults for them would be exactly the
fabrication the research document warns against.

New module `src/caddai/statistics/population_prior.py`:

```python
class PopulationPriorParameters(BaseModel):
    family: ShotDistributionFamily = ShotDistributionFamily.BIVARIATE_STUDENT_T
    carry_scale_metres: float = Field(gt=0)
    lateral_scale_metres: float = Field(gt=0)
    correlation: float = Field(gt=-1.0, lt=1.0)
    degrees_of_freedom: float = Field(gt=2.0)
    # same _require_finite field_validator pattern as shot_distribution.py


class PopulationPriorConfidence(StrEnum):
    LOW = "low"
    MODERATE = "moderate"
    HIGH = "high"


class PopulationPriorProvenance(StrEnum):
    EVIDENCE_INFORMED_PROVISIONAL_CONFIG = "evidence_informed_provisional_config"
    CADDAI_CALIBRATION = "caddai_calibration"
    FITTED_MODEL = "fitted_model"


class HandicapBand(StrEnum):
    PLUS = "plus"
    LOW = "low"
    MID = "mid"
    HIGH = "high"


class PopulationPriorResult(BaseModel):
    parameters: PopulationPriorParameters
    confidence: PopulationPriorConfidence
    provenance: PopulationPriorProvenance
    config_version: str = Field(min_length=1)
    handicap_band: HandicapBand
    club_category: ClubCategory
    handicap_index: float  # echoes resolved input, traceability only


def resolve_population_prior(
    handicap_index: float, club_category: ClubCategory
) -> PopulationPriorResult: ...
```

`resolve_population_prior` validates `handicap_index` (finite, in range —
see §3) and `club_category` (must be a supported full-swing category — see
§4) itself and raises `ValueError` on violation (plain function, not a
wrapping Pydantic model — consistent with `caddai.course.distance`
precedent).

**M3↔M4 pipeline note** (document in code comments for M4.3's implementer):
a future `PlayerShotDistribution` is built from `carry_location_metres`/
`lateral_bias_metres` (onboarding, M4.3) plus
`carry_scale_metres`/`lateral_scale_metres`/`correlation`/
`degrees_of_freedom` (this issue's `PopulationPriorParameters`, until M4.5
personalisation supersedes them).

### 3. Handicap representation

- `handicap_index: float` parameter to `resolve_population_prior`.
- Range: `-10.0 <= handicap_index <= 54.0` (WHS Handicap Index practical
  bounds; plus-handicap golfers go down to "+10" represented as `-10.0`;
  `54.0` is the WHS-defined maximum for all players). Enforced inside
  `resolve_population_prior`, not as a reusable Pydantic type.
- Plus-handicap (negative) values are valid and map to `HandicapBand.PLUS`
  — never assume `handicap_index >= 0`.
- Non-finite values (`NaN`/`+inf`/`-inf`) rejected via `math.isfinite`
  before the range check.
- Both non-finite and out-of-range violations raise `ValueError`.

### 4. Numeric lookup table — introduced now, small and explicitly provisional

Ship a real (small) table now: a contract with no populated data would
leave "lookup for representative handicap bands/club categories" and
"rejection of out-of-range/unknown inputs" untestable per the issue's
acceptance criteria.

- **Location:** `src/caddai/statistics/population_prior_config.py` —
  separate from `population_prior.py`'s domain types, so replacing this
  file's contents (or swapping in a fitted-model lookup) later never
  touches `PopulationPriorResult`/`resolve_population_prior`'s signature
  (ADR 0007 "stable interface, replaceable implementation").
- **Club-category coverage:** only the 5 full-swing categories — `DRIVER`,
  `FAIRWAY_WOOD`, `HYBRID`, `IRON`, `WEDGE`. `PUTTER` and `OTHER` are
  **unsupported** (`resolve_population_prior` raises `ValueError`) — putting
  is a behaviourally distinct regime (research doc) and `OTHER` has no
  defined mechanics to condition on. `FAIRWAY_WOOD`/`HYBRID` hold
  **identical** provisional values (research doc groups them together) —
  document why in a code comment.
- **Handicap bands** (4, half-open range containment, no interpolation):

  | Band | Range (`handicap_index`) |
  |---|---|
  | `PLUS` | `[-10.0, 0.0)` |
  | `LOW` | `[0.0, 9.0)` |
  | `MID` | `[9.0, 18.0)` |
  | `HIGH` | `[18.0, 54.0]` |

  No interpolation between bands — interpolating would imply a continuous
  handicap→dispersion function the evidence doesn't support (only
  *direction* of the handicap effect is evidence-backed; the numeric
  surface is an unresolved gap per the research doc).
- **Shape:** `dict[tuple[HandicapBand, ClubCategory], PopulationPriorParameters]`
  (4 bands × 5 categories = 20 cells, 16 distinct after the
  `FAIRWAY_WOOD`==`HYBRID` alias).
- **Versioning/marking:** module-level `POPULATION_PRIOR_CONFIG_VERSION =
  "m4.2-provisional-v1"`, copied into every `PopulationPriorResult.
  config_version`. Every cell gets `confidence=PopulationPriorConfidence.LOW`
  and `provenance=PopulationPriorProvenance.
  EVIDENCE_INFORMED_PROVISIONAL_CONFIG` uniformly — the research doc
  classifies handicap × club-category carry/lateral scale, correlation, and
  degrees-of-freedom as **unresolved evidence gaps** (items 1–3), so no
  cell claims `MODERATE`/`HIGH` confidence yet.
- **Module docstring** must reference
  `docs/research/m4-probabilistic-golfer-model.md` ("Unresolved evidence/
  calibration gaps", items 1–3) and state explicitly that numeric values are
  illustrative/provisional CaddAI configuration, not validated population
  data.
- **Numeric-value authoring constraints** (Player Engineer, not prescribed
  literally by the Architect): driver gets the tightest handicap-conditioned
  spread differentiation (strongest evidence, Betzler et al.); lower
  handicap bands get smaller scale values than higher bands within each
  category (directionally evidence-backed); `degrees_of_freedom`/
  `correlation` may be held constant across bands within a category where
  there's no basis to vary them — do not manufacture a fake gradient.

### 5. Provenance/confidence metadata shape

- `PopulationPriorProvenance` `StrEnum`: `EVIDENCE_INFORMED_PROVISIONAL_CONFIG`
  (this issue's only in-use value), `CADDAI_CALIBRATION`, `FITTED_MODEL`
  (unused until a future model swap — present so ADR 0007's replaceability
  claim is true on day one).
- Confidence is a **3-value qualitative `StrEnum`** (`LOW`/`MODERATE`/
  `HIGH`), not a numeric 0–1 score — a numeric score would manufacture false
  precision the evidence doesn't support. Minimum structure needed to
  distinguish config-guess vs. calibrated vs. validated later; no ML
  metadata framework.

### 6. ADR status

- **ADR 0006 → Accepted**: `PlayerShotDistribution` is already fully
  implemented matching the ADR's construction; flip status as a small docs
  change in this PR.
- **ADR 0007 → Accepted**, conditioned on: (a) stable/replaceable interface
  (`resolve_population_prior` signature need not change for a future
  fitted-model swap); (b) locally embeddable (plain Python module, no
  network/file fetch); (c) provisional values visibly marked (`confidence`/
  `provenance`/`config_version` present, correctly `LOW`/provisional); (d)
  no new dependency. QA/Reviewer verify these four conditions explicitly
  before the Integrator's docs-consistency check treats the status flip as
  valid.
