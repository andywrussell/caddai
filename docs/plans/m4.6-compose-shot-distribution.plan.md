# M4.6 — Compose `PlayerShotDistribution` into Club/Player

GitHub issue: [#54](https://github.com/andywrussell/caddai/issues/54)
(parent [#10](https://github.com/andywrussell/caddai/issues/10), M4).
Depends on M4.3 (#51), M4.5 (#53) — both merged into `main`. Blocks M4.8
(#56).

## Goal

Compose `PlayerShotDistribution` into `Club`/`Player` cleanly, wiring the
population -> onboarding -> personal pipeline (M4.2 -> M4.3 -> M4.5) into a
single composition entry point and a single read path, without duplicating
existing M3 concepts (`CarryDistribution`/`DirectionalDispersion`) and
without losing the M4.5 baseline-vs-current distinction. Composition/
integration only — no Monte Carlo, no environment/physics, no
course-relative mapping, no strategy, no persistence/database, no mobile/
API/cloud behaviour.

## Architect input (full review on file)

The CaddAI Architect subagent reviewed issue #54, ADR 0006, ADR 0007, the
current `caddai.player`/`caddai.statistics` code (including M4.3/M4.5), and
`tests/test_architecture_boundaries.py`, read-only, before implementation
began. Summary of binding decisions:

1. **Baseline field**: `Club.shot_distribution: PlayerShotDistribution |
   None = None` — exact name/type the issue suggests, with an explicit
   `None` default so every existing `Club(...)` construction site (tests,
   `demo.py`, `with_expected_carry`) is unaffected. Holds the immutable
   baseline (onboarding/population-prior cold-start distribution) only —
   nothing ever writes a shrinkage posterior back into it.
2. **`None` semantics**: uniformly "no baseline composed yet." `Club`
   stores no second marker for *why* (not-yet-onboarded vs. `PUTTER`
   deferred vs. `OTHER` not-modelable) — that's derived on demand from
   `club.category` via the existing `club_category_support_status()`
   (`caddai.statistics`), never stored redundantly.
3. **Current distribution: derived, not stored.** No second `Club` field.
   A derive-on-demand function call is the only shape that can't
   accidentally violate M4.5's batch-recompute contract (always
   `baseline + complete current history`, never a previous posterior fed
   back in) — there is no persisted "current" value to misuse as a
   baseline. Recomputation cost is one pass over one club's shot history,
   consistent with the cost model M4.5 already accepted.
4. **New module**: `src/caddai/player/shot_distribution.py` — plain
   composition functions (not model methods; matches convention —
   `Club.expected_carry_metres`/`with_expected_carry` remain the two
   existing exceptions, not a precedent to extend):
   - `compose_club_shot_distribution(*, handicap_index, club_category,
     reported_carry_metres, carry_provenance, common_miss, club_name,
     shot_history, shot_shape=ShotShape.STRAIGHT, config=None) ->
     ClubShotDistributionComposition` — the single M4.2 -> M4.3 -> M4.5
     composition entry point, called at (re-)onboarding time. Calls
     `resolve_population_prior`/`personalise_shot_distribution` itself
     (caller supplies raw onboarding inputs, not a pre-built
     `OnboardingPersonalisationResult`). Propagates
     `ValueError`/`PopulationPriorUnsupportedCategoryError` unmodified
     (including `PUTTER`=`DEFERRED`/`OTHER`=`NOT_MODELABLE`). Returns
     `baseline_shot_distribution` (persist onto `Club.shot_distribution`
     explicitly — no hidden mutation), `current_shot_distribution`
     (immediate use only, not persisted), `onboarding`
     (`OnboardingPersonalisationResult`), `update`
     (`ShotDistributionUpdateResult`).
   - `resolve_current_shot_distribution(club, shot_history, config=None)
     -> ClubShotDistributionResolution` — the ongoing M4.8/`simulation`
     read path against an already-baselined `Club`. Never calls
     `resolve_population_prior`/`personalise_shot_distribution` (those are
     onboarding-time only). Returns `shot_distribution:
     PlayerShotDistribution | None` and `support_status:
     ClubCategorySupportStatus` (reused from `caddai.statistics`, not a
     new competing enum) — `None`/`SUPPORTED` means "not yet onboarded";
     `None`/`DEFERRED` means `PUTTER`; `None`/`NOT_MODELABLE` means
     `OTHER`; present/`SUPPORTED` means resolved and ready to use.
     `support_status` is always recomputed from `club.category`,
     independent of whether `shot_distribution` happens to be populated.
   - Two functions, not one: they solve different call patterns
     (`onboarding inputs -> baseline` vs. `existing Club + fresh history
     -> current`) — collapsing them would force every M4.8 read-path call
     to also carry onboarding scalars it doesn't have.
   - Both functions take `club`/`club_name` + `shot_history` directly, not
     `Player` + a name to look up — avoids inventing a duplicate-club-name
     disambiguation policy that isn't specified anywhere today. **Flagged,
     not solved in this issue**: `Club.name`/`ShotRecord.club_name` remain
     plain strings with no uniqueness constraint across a `Player`'s bag;
     no `Player`-level name-lookup convenience function is added — callers
     supply the specific `Club` object. Document as a known limitation
     (`docs/player-model.md`, mirroring the existing
     `ShotRecord.club_name`-not-cross-validated note), optionally added to
     `docs/backlog.md`.
5. **M3 vs M4 authority**: M3 (`CarryDistribution`/`DirectionalDispersion`)
   remains authoritative for unmigrated consumers (`Club.expected_carry_metres`,
   current `strategy.recommend_club()`, which only reads
   `expected_carry_metres`). M4 (`PlayerShotDistribution`, via
   `resolve_current_shot_distribution`) becomes authoritative for any
   consumer built against it (`caddai.simulation`, M4.8; later `strategy`).
   No code ties the two together — no validator, computed field, or
   conversion function links `carry_distribution.mean_metres` to
   `shot_distribution.carry_location_metres`; they may legitimately hold
   different numbers for the same club. This is a **documentation**
   discipline, not a code one (enforcing consistency would itself be the
   coupling ADR 0006 rejects): `Club`'s docstring and
   `docs/player-model.md` state that once `shot_distribution` is populated
   for a club, `carry_distribution`/`dispersion` are not read by any
   `shot_distribution`-aware consumer, by convention — no consumer should
   read both and blend/average.
6. **ADR impact: none.** ADR 0006 already explicitly names this exact
   composition as its deferred M4.6 consequence; ADR 0007 is untouched.
   Additive, defaulted field; no new dependency; no ownership/dependency-
   direction change; no `PopulationPrior` replaceability-contract change.
7. **Ownership**: Player Engineer (spans `caddai.player`/`caddai.statistics`
   per module ownership, but this issue makes no `caddai.statistics`
   changes — it only composes existing `caddai.statistics` exports).
8. **No `NEEDS_DECISION` conditions.**

## Tasks

### Task 1 — QA Engineer: test design

Write/extend tests from the acceptance criteria before/alongside
implementation:

- New `tests/test_player_shot_distribution.py` covering at minimum:
  - `compose_club_shot_distribution` with a supported club category and
    empty history: `current_shot_distribution == baseline_shot_distribution`
    (zero history -> equals baseline); `onboarding`/`update` bookkeeping
    populated correctly.
  - `compose_club_shot_distribution` with relevant club history: current
    distribution differs from baseline per M4.5 shrinkage semantics.
  - Unrelated club's history does not affect another club's resolved
    current distribution (history filtered by `club_name`/`club.name`).
  - Repeated calls to `resolve_current_shot_distribution`/
    `compose_club_shot_distribution` with identical inputs are
    deterministic/idempotent (no RNG).
  - The same baseline must be reused every call — verify feeding a
    previous posterior back in as baseline (i.e. calling
    `resolve_current_shot_distribution` on a `Club` whose
    `shot_distribution` was overwritten with a prior posterior) is not
    something the API does implicitly; `Club.shot_distribution` is never
    mutated by `resolve_current_shot_distribution` itself (baseline
    immutability — call it twice, confirm `club.shot_distribution` is
    unchanged both times).
  - `ClubCategory.PUTTER` -> `compose_club_shot_distribution` propagates
    `PopulationPriorUnsupportedCategoryError(status=DEFERRED)`;
    `resolve_current_shot_distribution` on a `PUTTER` `Club` with
    `shot_distribution=None` returns `(None, DEFERRED)`.
  - `ClubCategory.OTHER` -> same shape with `NOT_MODELABLE`.
  - A supported-category `Club` with `shot_distribution=None` (never
    onboarded) -> `resolve_current_shot_distribution` returns
    `(None, SUPPORTED)`.
  - Invalid/non-finite onboarding inputs propagate `ValueError` unmodified
    (mirrors `personalise_shot_distribution`'s own tests).
  - Serialization/round-trip: a `Club` with a populated `shot_distribution`
    round-trips through `model_dump()`/`model_validate()` (or
    `model_dump_json()`/`model_validate_json()`) with an equal
    reconstructed `shot_distribution`.
- `tests/test_player_models.py` additions (per issue acceptance criteria):
  - A `Club` with no `shot_distribution` behaves exactly as before
    (regression) — existing construction/serialization tests continue to
    pass with the field defaulting to `None` and, where relevant, an
    explicit case asserting `Club(...).shot_distribution is None`.
  - A `Club` with a populated `shot_distribution` round-trips correctly.
  - `Club.with_expected_carry(...)` still leaves `shot_distribution` as
    `None`.
- `tests/test_architecture_boundaries.py`: add
  `REPO_ROOT / "src/caddai/player/shot_distribution.py"` to the `player`
  boundary's `source_files` tuple.
- Full existing suite (`tests/test_player_models.py`,
  `tests/test_strategy_recommend.py`, `tests/test_strategy_demo.py`) must
  continue to pass unmodified for equivalent inputs (additive, defaulted
  field only).
