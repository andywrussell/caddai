# Pre-mobile offline synthetic validation harness requirement (documentation-only)

## Goal

Before M4 closeout, capture a new pre-mobile/M5.5 architecture requirement:
CaddAI needs a future offline synthetic simulation/validation harness that
runs large numbers of deterministic synthetic golf rounds — synthetic
golfer profiles on real canonical CaddAI course geometry — by invoking the
actual production `strategy`/`simulation` engine (never a separate mock or
reimplemented strategy engine), to bridge the gap between unit/integration
tests and real golfer mobile field testing. Also record that, after M4
closeout, the project pauses before detailed M5 implementation planning to
jointly reassess M5+ milestones now that pre-mobile architecture scope has
grown. This is a **documentation-only** change: no harness implementation,
no synthetic player generator, no round simulator, no course simulation, no
property-based framework, no Rust bindings, no evaluation dashboards, no
regression thresholds, no CI validation runs, no new repository, and no
change to completed M4 implementation scope.

## Architect input

CaddAI Architect (read-only) review findings:

- No ADR required: no new runtime dependency, public API contract change,
  canonical-unit change, module-ownership change, or dependency-direction
  change, and no change to the deterministic-strategy (ADR 0001) or
  offline-first (ADR 0005) principles. The requirement's core property —
  the harness must invoke the real production core and never duplicate/
  reimplement `strategy`/`simulation` — reinforces ADR 0001's testability
  rationale rather than changing it.
- M5.5 ("Runtime & Offline Architecture (research spike)") is the correct
  existing anchor; do not add a new numbered milestone. M5.5 already carries
  analogous non-functional cross-cutting scope (the monitoring/evaluation
  event-contract bullets added by a prior documentation task); a synthetic
  validation harness is the same kind of pre-M7 infrastructure requirement.
- `docs/architecture.md` should gain one short new sibling section (not
  nested inside "Offline-first active round") stating the harness is a
  test-time *caller* of `strategy`/`simulation`'s existing public interface
  — architecturally identical in shape to `cli`/`api` — depending inward,
  never the reverse, with `strategy`/`simulation` never importing or
  becoming aware of it. It should point to `roadmap.md` M5.5 and
  `decision-journal.md#monitoring-vs-evaluation` rather than duplicating
  the validation-level/scenario/versioning detail, which belongs at
  roadmap/backlog altitude only.
- No dependency-direction or module-ownership change: the harness doesn't
  shift `strategy`/`simulation` ownership from the Strategy Engineer; its
  own future repository/component ownership is correctly deferred to the
  M5.5 checkpoint, not decided now.
- Trim before drafting: keep the 3 validation levels and metamorphic
  examples as illustrative, not an exhaustive taxonomy; keep Rust-parity
  levels and CI placement as clearly open options; compress the
  multi-repo/agentic content to short statements, not a sub-bullet spec, in
  `roadmap.md`; keep `backlog.md` entries as short forward-pointers, not a
  second prose copy.
- `docs/prfaq.md`: the existing "Ultimately, trust will need to be
  validated through real on-course testing" line (in the "Why should a
  golfer trust CaddAI?" FAQ) is the natural anchor for one added sentence
  distinguishing internal/synthetic self-checking from real-world
  validation, in product/customer-trust register — no implementation
  terminology (e.g. avoid the word "harness" there).
