# M4.1 — `PlayerShotDistribution` domain type

GitHub issue: [#49](https://github.com/andywrussell/caddai/issues/49)

## Goal

Define `PlayerShotDistribution`, the bivariate Student-t shot-production
domain type required by [ADR 0006](../adr/0006-player-shot-distribution-bivariate-student-t.md),
in `caddai.statistics`. Domain representation only — no sampling, no
`PopulationPrior`, no onboarding personalisation, no simulation, no
strategy, no `Club`/`Player` composition (M4.6).

## Architect input

CaddAI Architect reviewed the proposed mathematical parameterisation and
boundary decisions. **No ADR required** — ADR 0006 already binds the
family/correlation/heavy-tail decision; nothing here changes a dependency,
public API, canonical unit, module ownership, or the deterministic-strategy/
offline-first principles.

Confirmed decisions:

1. **`degrees_of_freedom` (ν) must satisfy `ν > 2` (strict).** Not `>= 2`,
   not `> 1`, not `> 0`. Rationale: for the standard bivariate Student-t
   construction `X = μ + Z / sqrt(W/ν)` (`Z ~ N(0, Σ)`, `W ~ chisquare(ν)`,
   per ADR 0006), the mean exists only for `ν > 1` and the covariance
   `Cov(X) = (ν/(ν-2))·Σ` exists (is finite) only for `ν > 2`. Since CaddAI
   needs both expected carry and finite dispersion/covariance to be
   always-valid domain quantities (not something every downstream consumer
   must special-case), the type-level invariant is `ν > 2`.
2. **`correlation` must satisfy the open interval `(-1, 1)` (strict), not
   `[-1, 1]`.** Exact ±1 makes the 2×2 scale matrix singular/rank-deficient,
   which breaks the `numpy.random.Generator.multivariate_normal` step of
   the ADR 0006 sampling construction (even though sampling is not
   implemented in this issue) and is not a meaningful "shot production"
   distribution (all mass on a line). Rejected at construction time.
3. **`carry_scale_metres`/`lateral_scale_metres` must be strictly `> 0`**,
   diverging intentionally from M3's `CarryDistribution.stddev_metres`/
   `DirectionalDispersion.lateral_stddev_metres` (which allow `0.0` as a
   "no data yet" placeholder convention). `PlayerShotDistribution`
   represents the actual joint production distribution, not a placeholder;
   zero scale on either axis is the same singular-scale-matrix failure mode
   as ±1 correlation.
4. **Field names confirmed**: `family`, `carry_location_metres`,
   `lateral_bias_metres` (reusing the exact `DirectionalDispersion` name/
   sign convention for consistency), `carry_scale_metres`,
   `lateral_scale_metres`, `correlation`, `degrees_of_freedom`.
   **`family` is a `StrEnum`** (`ShotDistributionFamily`), not
   `Literal[...]`, for consistency with every other discriminator/
   categorical field in the codebase (`FeatureType`, `ClubCategory`,
   `WindDirection`, `LieType`).
5. **Option B confirmed**: `PlayerShotDistribution` holds its own
   independent joint parameters — it does **not** compose or convert to/
   from `CarryDistribution`/`DirectionalDispersion` in this issue (that
   coupling risks either misusing Gaussian-shaped fields for Student-t
   scale, or mutating M3 primitives, both of which ADR 0006 rules out).
   Composition is M4.6. Implied-covariance/stddev **computed properties**
   are in scope (pure derived math internal to this one type, not a
   cross-type conversion):
   - `implied_covariance_metres_sq` — 2×2 covariance matrix
     `(ν/(ν-2))·Σ`, as a nested tuple.
   - `implied_carry_stddev_metres` / `implied_lateral_stddev_metres` —
     `sqrt(ν/(ν-2)) · scale`, explicitly **not** equal to the scale
     parameters themselves.
   - Because the `ν/(ν-2)` factor scales the whole covariance matrix
     uniformly, `correlation` is literally the distribution's Pearson
     correlation coefficient (not merely a scale-matrix parameter needing
     separate interpretation) — document this explicitly.
6. **New module**: `src/caddai/statistics/shot_distribution.py` (not an
   extension of `models.py`), re-exported from `caddai.statistics.__init__`.
   `tests/test_architecture_boundaries.py`'s `statistics` `source_files`
   tuple must be updated to include the new file (that test enumerates
   files explicitly; it does not glob the package, so a new file gets zero
   boundary coverage unless added).
7. **No ADR needed.**

Additional Architect findings applied to scope:

- ADR 0007's provenance/confidence metadata is deferred to M4.2
  (`PopulationPrior`), per ADR 0007's own "or an adjacent type" allowance —
  **not added to `PlayerShotDistribution` in this issue.** State this
  explicitly in the PR description so it reads as a deliberate scope
  decision, not an oversight.
- Computed-property return types must be explicit (e.g.
  `tuple[tuple[float, float], tuple[float, float]]`) for mypy strict.
- (Not part of this issue) Architect flagged stray duplicate ADR files
  (`docs/adr/0006-... 2.md`, `docs/adr/0007-... 2.md`) not listed in
  `docs/adr/README.md` — reported to the human separately, out of scope
  for this change.
