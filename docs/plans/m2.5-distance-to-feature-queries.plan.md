# M2.5 — Distance-to-feature queries

GitHub issue: [#7](https://github.com/andywrussell/caddai/issues/7)

## Goal

Implement point-to-feature distance queries in `caddai.course`: distance to
green front/centre/back, and distance to carry a hazard along a line of
play — pure geometric queries against the M2.4.5 (#22) boundary geometry,
with no strategic decision-making (that remains the Strategy Engineer's
job, M5+).

## Architect input

The CaddAI Architect reviewed this issue (read-only) and recommended:

- **Coordinate-frame consistency (human-specified, non-negotiable)**: every
  query that combines a player position, an aim point, and a feature's
  `boundary` must project all three into **one common local-metre frame,
  freshly, per call**, using `player_position` as the shared origin — never
  reusing `caddai.course.models._local_polygon`/`polygon_centroid`'s
  per-feature ad hoc origin (`boundary[0]`) for anything that also involves
  the player's position. Mixing local coordinates computed from two
  different origins is a class of bug this design must structurally
  prevent, not just avoid by convention.
- `player_position` is the correct choice of shared per-query origin
  (matches "distance from here" intuition; avoids introducing a durable
  hole-/course-level origin, which ADR 0003 explicitly declined to add and
  which isn't needed since every reported value is a distance from the
  player).
- Use `green.position` (the polygon centroid, per ADR 0003) as the implicit
  aim point for the green query, so "centre" and the front/back line-of-play
  direction share the same target. Must be documented explicitly as
  "distance to the green polygon's centroid" — **not** a pin/flag location,
  echoing ADR 0003's own centroid caveat. This is a known simplification
  (no `Hole.pin_position` concept exists yet); flag as a likely follow-up.
- Compute all three of front/centre/back via the same local-metre frame
  (not `gps.distance.haversine_distance_metres` for "centre") for internal
  consistency within one query's reported numbers.
- Use **signed** distance (vector projection / dot product with the unit
  player→aim direction) rather than plain Euclidean distance, so a
  boundary-crossing point behind the player naturally yields a negative
  value — this is how "point already past the feature" is modeled, with no
  special-case branching.
- Required robustness fixes before/while implementing:
  1. Guard `player_position == aim_point` (degenerate/undefined direction)
     with a clear `ValueError`.
  2. `polygon.exterior.intersection(line)` can return `Point`, `MultiPoint`,
     `LineString`, `MultiLineString`, or `GeometryCollection` (tangent to or
     overlapping an edge) — enumerate every component geometry's
     coordinates, don't assume `Point`/`MultiPoint` only.
  3. The "point on boundary" degenerate case must be asserted with
     `pytest.approx` (tolerance, e.g. 0.01 m consistent with ADR 0003), not
     exact zero — floating-point tangency after a fresh projection is not
     guaranteed bit-exact.
  4. Explicitly decide degenerate crossing counts:
     - **0 crossings** for `hazard_carry_distance`: expected/normal — return
       `None` ("not in play" for that line).
     - **0 crossings** for `green_front_centre_back_distances`: should be
       geometrically impossible (aim point = the green's own centroid, an
       interior point of the polygon, guaranteeing at least one crossing in
       each direction along the line) — raise a clear internal `ValueError`
       if it ever happens (defensive, not expected to be hit by valid data).
     - **Exactly 1 crossing** (tangent): `front_metres == back_metres` (or
       the single carry distance for the hazard case) — both equal that
       one signed distance.
     - **>2 crossings** (possible for a non-convex/concave ring, out of
       scope to fully model): "front" = the nearest (minimum signed
       distance) crossing, "back"/"carry" = the farthest (maximum signed
       distance) crossing, among all crossings found — documented as an
       explicit scope limitation, not silently wrong.
  5. The line segment used for intersection must extend far enough beyond
     the polygon in the aim direction, derived from the data (e.g. the
     max distance from `player_position`'s local point to any boundary
     vertex, times a safety multiple), not a magic constant — and must
     still work correctly when the polygon lies behind the player (aim
     point pointing away from the feature), so purely negative results are
     still captured.
  6. Add a fixture-convexity sanity test: assert the M2.4 fixture's green/
     bunker polygons are convex, since the "hand-computed expected values"
     acceptance criterion implicitly assumes the nearest/farthest-crossing
     simplification agrees with a full hand computation only when convex.
- **`tests/test_architecture_boundaries.py`'s `course` boundary must add
  `src/caddai/course/distance.py`** to its `source_files` tuple — otherwise
  the new module's dependency-direction is silently unchecked.
- **ADR 0004 required** (new — ADR 0003 explicitly deferred this exact
  decision to M2.5: "a shared course-/hole-level local-projection origin...
  is an open question, intentionally deferred to M2.5"). Must cover:
  1. The decision: no shared/durable origin — every query re-projects
     fresh, per call, using `player_position` as origin; why, vs. a
     canonical hole/course origin.
  2. Explicit statement that this projection is independent of, and must
     never be mixed with, `_local_polygon`'s per-feature origin from ADR
     0003 — state the invariant plainly.
  3. "Centre" = distance to the green polygon's centroid (not a pin/flag
     location), referencing ADR 0003's caveat.
  4. The signed-distance-via-vector-projection technique; formal
     definition of "front"/"back"/"carry".
  5. The concave-polygon non-goal (nearest/farthest crossing only) and
     degenerate crossing-count behaviour (0/1/>2), per the bullets above.
  6. Consequences: repeated per-query projection cost (intentionally not
     optimized, consistent with ADR 0003's precedent); ADR 0002's ~2 km
     small-area accuracy caveat still applies.
  7. Alternatives considered: canonical hole-level origin, aim-point-as-
     origin, `boundary[0]`-as-origin (each rejected, with why).
- No dependency-direction/module-ownership violation: `course/distance.py`
  imports only `caddai.course`/`caddai.gps`, matching the `course`
  boundary's already-approved prefixes; returns pure geometric values
  (`GreenDistances`, `float | None`), no coupling toward `strategy`/
  `simulation`.

## Tasks

1. **Course Engineer** — `src/caddai/course/distance.py` (new module):
   - `GreenDistances(BaseModel)`: `front_metres: float`, `centre_metres:
     float`, `back_metres: float`.
   - Private shared primitive, e.g. `_signed_line_boundary_crossings(
     player_position: Coordinate, aim_point: Coordinate, boundary:
     tuple[Coordinate, ...]) -> list[float]`: projects `player_position`
     (origin), `aim_point`, and every `boundary` vertex fresh into one
     common local-metre frame via `gps.projection.to_local`; guards
     `player_position == aim_point` with `ValueError`; builds a
     data-derived-length `shapely.geometry.LineString` from the local
     player point through/beyond the local aim point; intersects with
     `Polygon(boundary_local_points).exterior`; enumerates every
     intersection component (handling `Point`/`MultiPoint`/`LineString`/
     `MultiLineString`/`GeometryCollection`) into a flat list of local
     `(x, y)` crossing points; returns their signed distances (dot product
     with the unit player→aim direction vector), sorted ascending.
   - `green_front_centre_back_distances(player_position: Coordinate, green:
     Feature) -> GreenDistances`: raises `ValueError` if `green.boundary is
     None`; aim point = `green.position`; `centre_metres` = signed distance
     to `green.position` in the same frame (should equal the straight-line
     distance since it's the aim direction itself); front/back from the
     crossings list per the degenerate-count rules above (0 crossings →
     internal `ValueError`; 1 → front==back; ≥2 → min/max).
   - `hazard_carry_distance(player_position: Coordinate, aim_point:
     Coordinate, hazard: Feature) -> float | None`: raises `ValueError` if
     `hazard.boundary is None`; 0 crossings → `None`; 1 → that value; ≥2 →
     max (farthest/"carry" distance).
   - Full strict type hints; concise docstrings stating the frame-
     consistency invariant explicitly (never mix with `_local_polygon`'s
     per-feature origin) and the centroid-not-pin caveat for "centre".
   - No imports from `player`, `strategy`, `statistics`, `simulation`,
     `llm`, `api`, or `cli`.

2. **Course Engineer** — `tests/test_architecture_boundaries.py`: add
   `REPO_ROOT / "src/caddai/course/distance.py"` to the `course` boundary's
   `source_files` tuple.

3. **Course Engineer** — ADR `docs/adr/0004-distance-query-local-frame.md`
   (exact filename TBD), status `Accepted`, per the Architect's required
   contents above; cross-linked from `docs/adr/README.md`'s index.

4. **Course Engineer** — update `docs/course-engine.md`: replace "Distance
   calculations... remain planned (M2.5)" / "Hazard carry... remain
   planned (M2.5)" language with a description of the implemented
   `distance.py` API, its frame-consistency invariant, and scope limits
   (convex-polygon assumption for nearest/farthest crossing; centroid, not
   pin, for "centre"). Link ADR 0004.

5. **QA Engineer** — `tests/test_course_distance.py` (new file), deriving
   from issue #7's acceptance criteria:
   - Hand-computed happy-path test: given the M2.4 fixture course's hole 1
     polygon green (`course.holes[0].features[3]`, a known axis-aligned
     square) and a chosen `player_position`, hand-compute (by simple
     geometry, independent of calling the functions under test)
     front/centre/back and assert `green_front_centre_back_distances`
     matches within tolerance.
   - Hand-computed happy-path test for `hazard_carry_distance` against
     hole 2's polygon bunker (`course.holes[1].features[3]`, a known
     triangle) with a `player_position`/`aim_point` pair whose line of play
     crosses it, hand-computing the expected carry distance independently
     (e.g. via the affine-covariant triangle-centroid-style reasoning, or
     plain coordinate geometry on the projected points computed manually
     in the test, not by calling `_signed_line_boundary_crossings`).
   - Degenerate: `player_position` already past the green (both
     front/back negative) — construct a standalone scenario (not
     necessarily the fixture) with hand-computed expected negative values.
   - Degenerate: `player_position` exactly on a boundary edge/vertex — one
     signed distance ≈ 0 within tolerance (not exact-zero assertion).
   - `hazard_carry_distance` returns `None` when the line of play doesn't
     cross the hazard at all (aim point/direction chosen to miss it).
   - `ValueError` when `green.boundary`/`hazard.boundary` is `None`.
   - `ValueError` when `player_position == aim_point`.
   - Fixture-convexity sanity check: assert the fixture's green/bunker
     polygons used above are convex (e.g. via Shapely's
     `polygon.equals(polygon.convex_hull)` or equivalent), documenting why
     this matters for the nearest/farthest-crossing simplification.
   - Exactly-1-crossing (tangent) case: front==back (or single carry value).
   - A test asserting no frame-mixing regression: e.g., that results are
     identical regardless of an unrelated feature's own `boundary[0]`
     ordering/rotation (i.e., the query result must not depend on which
     vertex happens to be `boundary[0]` in the stored `Feature.boundary`
     tuple — a rotation of the same ring's vertex order must produce the
     same front/centre/back values within tolerance). This is the key
     regression test for the coordinate-frame-consistency requirement.

## Explicit non-goals

- No club selection, target selection, or risk assessment (Strategy
  Engineer, M5+).
- No pin/flag position concept — "centre" is the green polygon's centroid.
- No full concave-polygon multi-crossing modeling — nearest/farthest
  crossing only, documented as a scope limitation.
- No durable shared course-/hole-level local-projection origin — every
  query re-projects fresh, per call (ADR 0004).

## Parallelism

Single subsystem, single owner (Course Engineer) — no parallel engineer
tasks. QA Engineer test design proceeds alongside/ahead of implementation,
both on the same feature branch.

## Escalations

None beyond the ADR already scoped above (human has approved proceeding
with this design via the explicit coordinate-frame-consistency
requirement in this conversation). No new dependency (Shapely already
approved), no canonical-unit change, no ownership change, no
dependency-direction change.
